## 实现（全部 VERIFIED-RUN）
- `conf/templates/chat-bridge.tpl.js`（~200 行，node 内置零依赖）：spawn `goose acp`（JSON-RPC over stdio）+ 手写 WebSocket 服务（含帧解析/masking/心跳）+ 静态页托管。bridge **自己读 data/secrets.env** 注入 acp 子进程 env（不依赖 pc 环境快照——pc envsubst 是 server 启动时快照，restart 进程不刷新，踩过）。
- `conf/templates/chat.tpl.html`：妻子友好聊天页（状态点/气泡流/工具调用折叠行/正在干活提示/发送框大字）。
- `跟数字员工聊天.cmd` 重写：等桥就绪（30s）→ `msedge --app=http://127.0.0.1:8790`（**无地址栏伪窗口应用**，480x760）。
- pc 新增 `chat-bridge` 常驻进程（healthz 探针）；bootstrap 5d 段生成。

## 排障记录（未来会话的宝藏）
1. **双重序列化**：通知路径传了 stringify 后的字符串给 writeFrame（又 stringify 一次）→ 客户端收到带引号转义的字符串。教训：ws.send 统一收对象。
2. **ACP 空转**：LLM 端点不可达时 goose acp 不报错——静默 end_turn + used:0 tokens（goose run 则明确报错）。诊断靠 usage_update 的 used 字段。
3. **pc envsubst 快照**：pc 进程 env 在 server 启动时定死；secrets 后补的键 restart 进程不生效 → bridge 自读 secrets.env 根治。
4. **secrets.env 历史损坏**：早期 bootstrap 生成过单行文件（键空格相连）→ 解析出 undefined host → "Invalid base URL: relative URL without a base"。已重写干净 + 解析器 trim/CRLF 防御。
5. **ACP debug 手法**：ACP_DUMP 原始 stdout 落盘 + FWD 日志注入，十分钟定位双重序列化。
6. 9router 是 node 应用：taskkill node.exe 会连带杀它（本会话两次误杀）。
