# 2026-08-25 s14 — P29 工作区信息架构：双栏分层 + 会话生命周期 + .forge 元数据

## 设计驱动
用户指出 P28 后的三处结构缺陷（会话/工作区数量增长无生命周期；当前会话工作区不跟随在场；列表拍平且附件身份硬编码在 uploads/）。先出完整 IA 设计再动工，用户两处修正后定案：
- 删除走单向门（仅归档组内可删），首次删除给完整后果提醒，标志存内存不持久化；
- 附件=「拷入工作区的文件」这一事实，存于工作区根部 `.forge` JSON，与存放路径解耦。
另追加：轻量文件管理（新建文件/目录、重命名、删除）+ 文件行「↗ 本机办公软件打开」（复用 /open），不做应用内编辑器。全文见 ADR-0008。

## 实现
- 桥接新端点：`/api/ws/tree`（递归树,file/dir/link 三型,budget 400）、`/api/ws/link|unlink`（引入=junction,realpath 防环;取消只摘链接）、`/api/ws/delete`(孤儿/归档才可删,全库 junction 引用扫描守卫)、`/api/fs/new|rename|delete`(重命名跟随附件元数据+git 记录)、`/api/sessions/archive`(GET/POST)、`/api/workspaces` 增 state 字段(active/archived/orphan)。
- 上传写入 `.forge.attachments`;重命名同步改写;删除清理子路径。
- 前端右栏重构:双 Tab(本对话/浏览全部);本对话=自动跟随会话的真目录树+只看附件筛选+行内五操作;浏览全部=搜索/排序/状态片/分页(客户端30条)+行内引入表单(默认名可改,弃 prompt 弹窗——顺带修 IAB 自动吞 prompt 的测试阻塞)。
- 左栏:活跃组(悬浮📥)+折叠归档组(↩/✕);`.sdel` 由 hover-display 改为常驻低透明度(hover 提亮)——既可自动化测试又提升小白可发现性。

## 事故与修复:daily-mem 调度洪水(s14 最大发现)
- 现象:会话列表"空"。排查链:UI 过滤正常→数据到达(lastSessions=50)→类型构成 50/50 全是 scheduled→DB 里 scheduled 占 1765/1909。
- 根因:P8 验证配方 daily-mem 的 cron 被写成 `*/2 * * * *`(每2分钟),三天刷了 1765 个会话,把真实对话挤出 ACP session/list 的最新50条窗口。
- 处置:备份 DB→清库(purged 1765 sessions/4967 messages,剩 144 真实对话)→cron 复位 `0 9 * * *`→桥启动自动修剪护栏(scheduled 只留最新20)。这正是用户"会话数据变多怎么办"预言的第一次真实应验。

## 验证
- API 回路:tree 结构与附件标志、link 自引/不存在目标拒绝、fs 新建/改名/删除、archive 往返、workspaces state 字段,全绿。
- GUI:零 JS 错误;干净库上会话列表复活;归档→归档组→展开见 ↩/✕;浏览全部默认「活跃」片隐藏孤儿区;引入流程(行内表单)建链成功且树中 🔗 节点带源路径 tooltip 与 ✕;子树经 API 证实完整(UI 折叠不进 a11y 快照属预期)。

## 教训
- "列表空"这类症状要一路追到数据层分类构成,UI 层往往无辜。
- 定时任务的验证配置用完必须复位;凡有 cron,启动时就要配护栏(修剪)而不是信任外部配置永远正确。
- CSS :hover 门控的按钮对自动化不可点(无几何),常驻低透明度是双赢解。
