## 1. 事实基线（本会话代码级取证）

- 技能市场单源硬编码：`REMOTE_SKILLS = { repo:'anthropics/skills', ... }`（chat-bridge.tpl.js L430）。s56 管道=sync→data/cache/skills/manifest.json（_schema:1）→中文翻译/搜索→安装=缓存本地复制；s59 桥启动 15s 预热+24h 重拉。本地精选目录 forge/skills-repo（2 项）与远程清单并列展示。
- 技能安装落点 `.agents/skills/<dir>/`：安装=cpSync 递归，**无冲突检测、无来源记录**；agent 自进化（P11，skill-sediment 规范沉淀）与市场安装共用同一命名空间；内置技能 5 枚（see-image/skill-sediment/forge-selfcheck/artifact-versioning/scrape-table-to-db）同目录随包发。
- MCP 目录硬编码桥内 `MCP_CATALOG` 常量（L656）：3 项（sequential-thinking/memory-graph/fetch，全 MIT）；安装=后台 npm vendor+写 extensions mcp-* 块；s57 停用/卸载齐。
- 列表形态：市场清单文件态 JSON 一次全量返回，无分页（P29 分页 PAGE_N=30 只覆盖会话/浏览全部）；PG 只服务「妻子自建应用」每应用一库（阶段二 doctrine，s66 落地），桥自身状态走 STATE_SCHEMAS/migrateJsonAt 文件管线。
- 单源定性：anthropics/skills 是「开源样例库」非市场（桥内注释自认）——单源=单点，上游重构/清空无预警，生命周期不受本项目控制。

## 2. 归约（三次为什么）

### 2.1 主线 2：「源少」+「无来源区分」

- 为什么源少是问题？→ 妻子想扩展能力时，可装的供给有限。
- 为什么她需要更多供给？→ 表面是能力墙。**事实核查：无证据**。妻子真机 POC 刚启动（2026-09-05「可以打开运行」确认，任务链/EDR 待护航反馈），s49 使用统计尚无「能力不足」信号。点名者是用户（技术内测者），实际观察到的是结构风险，不是妻子的行为数据。
- 为什么结构风险成立？→ 两个实锤：(a) 单源=单点故障，且源是样例库；(b) 加任何源、任何 MCP 目录项都要改桥模板代码——「生态开放」被硬编码成常量。s55-56 已立外部资源接入域管道（sync→缓存→人话化→安装=本地复制，出网面收敛到 sync），但「源」这个入口漏了参数化，管道的最后一块缺失。

- 为什么无来源区分是问题？→ 三层：**实锤**=同名冲突无守卫（cpSync 直接覆盖；agent 自沉淀技能可被市场同名安装静默覆盖丢失原创内容，反之 agent 修订也可能污染市场原件——且 s55-56 已永久裁掉版本管理，覆盖即丢失原始版本）；**认知层**=妻子分不清「小 forge 自己攒的」和「外面装的」，出问题不知道卸哪个；**前瞻层**=多源之后「这技能从哪来」无处回答。

**归约结论：真问题 =「生态入口被硬编码」（机制缺一口）+「安装无来源记录」（缺陷级，今天就可能静默丢数据）。「供给少」本身是表象——机制通了，供给按闸门逐个进；未证实妻子撞墙前不做内容扩容。**

### 2.2 主线 3：「不分页」「不入 PG」「无后端支撑」

- 为什么数据形态是问题？→ 用户论证：扩源后清单膨胀、妻子数据应用数据膨胀，基础设施不提前规划事后难补。
- 膨胀量级核实：技能清单=manifest JSON 全量（现 21 项），多源后 3–5 源 ≈ 100–200 项 ≈ 100KB 级文本，浏览器一次渲染无压力；MCP 目录即使 20 项仍是半静态清单。「妻子数据应用数据膨胀」走 PG 阶段二每应用一库——**刚落地，已被承接**。
- 「事后难补」到底缺什么？→ 不是存储引擎，是 **schema 字段预留**：manifest 与安装记录今天不带来源字段，多源之后再补才是真难补。这由文件态 _schema 纪律（ADR-0009）承接，PG 不在场。「无后端支撑」是错误归约——桥就是后端，缺的是多源清单协议（一个 JSON 配置 + manifest 加一个字段）。

**归约结论：「不入 PG」是表象且当前形态是对的（桥状态≠应用数据，阶段三门槛已定死防重新谈判）；「不分页」当前是表象，真到 50+ 项时解法是复用 P29 前端分页，不动文件态。**

## 3. 张力裁决：验证优先于扩张 vs 用户点名

裁减原则挂起的是「商店/插件类**扩张**」，拆开看两者不矛盾：

- **机制开放化 ≠ 扩张**。源配置化与来源标记是把 s55-56 接入域管道补上最后一环、关掉一个缺陷级冲突面——结构性补课，diff 小、桥内自洽、不依赖真机验证。用户点名=第一输入源生效，本裁决解除挂起原则对「机制」部分的适用。
- **内容扩张维持挂起**。新技能源、新 MCP 目录项=供给内容，仍走闸门制（见切片 C 准入清单），由护航反馈/使用统计驱动，逐个过，不做批量扩容。
- v0.9.9 RC 已就绪未发布：本裁决全部切片入 v0.9.10，不动 RC。v0.9.10 已有在办项（离线升级 sha256 通道，docs/verdicts/2026-09-05-offline-upgrade-sha.md），与本裁决切片无耦合，可并行排期。

## 5. 切片（一次会话一片；回归线=e2e 45/45 + fuzz 44/44 + 新增断言不降线）

### 切片 A：技能来源记录 + 冲突保护（S1，第 1 候选）

改什么：

- 安装写标记：`.agents/skills/<dir>/origin.json`（_schema:1，入 STATE_SCHEMAS）：`{ _schema:1, source, repo, branch, installed_at }`。source 枚举 `market | self | local`（local=skills-repo 本地目录安装，随包精选）；repo+branch 即源身份，天然兼容 S2 多源，无需二次迁移。market/local 安装由桥写；self 由 skill-sediment 规范加一行「沉淀时写 origin.json {source:'self', installed_at}」（改 SKILL.md 一行，agent 不守规范的降级=被视为本机技能，可接受，不写强制机制）。
- 冲突语义（/api/skillstore install POST）：目标已存在且无 origin.json 或 origin.source='self' → **拒绝**，人话（「这个名字小 forge 自己在用，先换个技能名」）；origin.source='market'|'local' → 允许覆盖（即唯一「更新」语义）。uninstall 随目录删除 origin.json（现状逻辑天然覆盖）。
- UI：技能行来源徽标（🌐+源名 / 无标=本机）。已装技能全量清单+按来源过滤的管理面板**本轮不做**（现状 UI 无此面，商店行内徽标已回答「从哪来」；挂起触发器=护航反馈妻子混淆再立）。

验收标准：

1. 三来源实景：市场装一枚（origin.json 生成+徽标）、模拟 sediment 写一枚（source:self）、bundled 存量一枚（无文件=本机）——列表可区分。
2. 冲突矩阵：market-over-self 拒（人话）、market-over-market 放行、local 安装写 origin、卸载后标记随目录消失。
3. goose 与 agentskills.io 规范对目录内额外文件 origin.json 无感知（技能加载回归通过；若不容忍，预案 B=标记载体改 SKILL.md frontmatter 扩展字段）。
4. fuzz 增断言：origin.json 解析容错（坏 JSON/缺字段→按本机处理不炸）、冲突分支、白名单同门。

风险：存量 v0.9.9 已装远程技能升级后无 origin（显示「本机」，cosmetic，接受）；agent 漏写 self 标记（降级=本机，接受）。

### 切片 B：技能市场源配置化（S2，第 2 候选，依赖 A 定案的标记载体）

改什么：

- `data/config/skill-sources.json`（_schema:1，首启不存在则由内置默认生成=[anthropics/skills 单条 enabled]）；fetchAllRemoteSkills/listRemoteSkills 遍历 enabled 源；manifest 条目加 `source:{repo,branch}`（存量条目迁移幂等补默认源）。
- sync/缓存/搜索/翻译/预热/安装/卸载全链复用零改动；多源同名 dir：manifest 先到保留、后到跳过（journal 留痕）。
- 源管理无 UI（见否决项 4）：加源=编辑 JSON 文件。

验收标准：

1. 实测加第二源（真实可达的开源技能 repo，主控选型过目+许可证白名单适用）→ 改 JSON 零代码 → sync→列表→安装→卸载全链 GUI 实景通过；第二源候选当轮缺位时，机制验收=单源经配置文件驱动回归（删配置重生成/改 branch 生效），真实第二源验收挂起至选型完成。
2. 缓存 <24h/预热/翻译预算不回归（多源翻译沿用 10 条/批截 150，后台化不阻塞）。
3. 旧 manifest 迁移幂等；fuzz 增多源合并/同名跳过断言。

风险：多源拉取总时长线性增长（预热后台化，接受）；新源内容质量（技能=纯文本无执行面，风险低于 MCP；源准入=人工过目，不做自动扫描）。

### 切片 C：MCP 目录配置化 + 准入清单（S3，第 3 候选）

改什么：

- `data/config/mcp-catalog.json`（_schema:1，首启生成现 3 条默认）；/api/mcpstore GET/POST 读配置（安装/停用/卸载白名单随配置，逻辑零改动）。
- **MCP 新目录项准入清单**（落档本裁决，护栏=人工流程，不写扫描代码）：①许可证白名单（包本体；无 LICENSE 文件沿 s54 标注来源声明先例）；②goose v1.46 实装挂载+真调一次（s54 fetch 选型流程复用）；③npm 源可达、包有维护方；④MCP SDK 大版本护栏（backlog 条目激活：goose 旧 spec 与 2026-07-28 stateless 规范协议错位风险，包升级即触发复检）。每入一枚必留 journal 选型记录。

验收标准：

1. 3 项默认零回归（列表/安装/停用/卸载 GUI 实景）。
2. 配置回环：改 JSON 增删条目零代码生效（dev 验证）。
3. 真实第 4 枚**不做承诺**——护航反馈给出真实需求且过四条闸门才入，届时验收=全链实景（安装→重启挂载→goose 真调）。

风险：配置化降低准入摩擦→乱加包（缓解=准入清单+选型留痕强约束）；catalog JSON 与 config.yaml bootstrap 块漂移（安装/卸载同门逻辑不变，配置只是目录来源）。

### 切片 D：分页（S4）——挂起，不排期

- 触发器：任一市场清单渲染 >50 项，或妻子/用户实测翻页卡顿反馈。
- 预案：P29 PAGE_N=30 前端分页模式复用，manifest 文件态不动，零后端改动。

## 6. 明确否决项（防重新谈判）

1. **市场清单/桥状态入 PG**——否决。桥状态有专门文件管线（STATE_SCHEMAS/migrateJsonAt，ADR-0009 schema 纪律）；PG 阶段二 doctrine 边界=「妻子自建应用每应用一库」；阶段三门槛已定死（真机消息量近 1 万或搜索负反馈），不因「提前规划」叙事重开。真正要提前规划的是 schema 字段，本裁决 S1/S2 已落。
2. **技能版本锁定/升级管理**——沿袭 s55-56 永久裁掉，不翻案。market-over-market 覆盖=唯一更新语义，够用。
3. **自动许可证/安全扫描器**（MCP 依赖树扫描、源内容自动审查）——否决。两次人工选型（s46/s54）已验证流程可行；技能纯文本无执行面；自动化=过度工程。
4. **源管理 UI（妻子界面加任意源）**——否决。源=配置文件操作，面向技术用户/主控；妻子扩展能力的入口是「装技能」，不是「加源」。防供应链面失控与形态滑向插件管理器。
5. **现在做分页**——否决（触发器制，切片 D）。
6. **批量扩容供给**（一次加 N 源/N 个 MCP 目录项）——否决。无需求证据；逐个过闸门，护航反馈/使用统计驱动。
7. **s42「sync 进 skills-repo」路线**——作废（§4），防未来按旧预留施工造成 skills-repo 与缓存双写漂移。

## 7. 非目标

- 不动 v0.9.9 RC；不做真机护航变更；不承诺任何具体新源/新 MCP 的内容扩容；不做已装技能全量清单管理面板；不改 skills-repo 本地目录角色；不动 goose/faucet 内部（零二开纪律）。
