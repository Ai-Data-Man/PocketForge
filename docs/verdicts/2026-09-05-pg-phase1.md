# 裁决书：ADR-0011 阶段一（PG 基础设施接线）设计与验收

- 日期：2026-09-05 / 裁决人：pf-pm / 执行：pf-engineer
- 边界声明：全部裁决在 ADR-0011 Accepted 范围内（zonky 渠道进树 + pc 托管 + initdb 三保障 + localhost 单端口）。不含任何业务库迁移。
- 新增实证（2026-09-05，本开发机，PG 17.11.0）：zonky jar 全量下载 23,812,556 字节；解包恰好 3 个 exe（initdb/pg_ctl/postgres）+ dll + share，解压态 125MB（bin 68M/share 27M/lib 7.3M）；initdb -D -E UTF8 --locale=C -A trust -U postgres 实测 9.0s；postgres -p 55432 -c listen_addresses=127.0.0.1 -c max_connections=20 启动、pg_ctl status 探活 exit 0、fast stop 全链通；空集群 40MB。npm 渠道 registry 元数据核验：所有版本线均为 beta（无稳定版）。
- jar 已留 downloads/zonky-pg-17.11.0.jar 供复用（gitignored）。

## 1. 分发渠道：zonky maven jar（pin 17.11.0）
maven central io/zonky/test/postgres/embedded-postgres-binaries-windows-amd64/17.11.0。决策性理由：npm 渠道全线 beta，无一条稳定版本线——把只有 beta 标签的制品 pin 进生产交付树违背 pinned-stable 纪律。zonky jar 23.8MB 压缩态；两渠道 checksums 机制等价（tools/checksums.txt 本就是 fetch 后自生成）；fetch.sh 改造三行级：curl jar → unzip 取 postgres-windows-x86_64.txz → tar -xJf，本机 xz + GNU tar 1.35 已验可用，零新工具。版本 17.x 最新稳定 17.11.0，不取 18.x。解包只在开发机 fetch 时发生，bin/pg/ 落净树（3 exe + dll + share），目标机零解包工具。fallback 预授权：maven central 断供时 npm tgz（同 zonky 血统）可作 fallback 渠道，无需重开选型。

## 2. 数据目录：首次启动现场 initdb，路径 ${FORGE_ROOT}/data/pg
决定性论据是打包架构：tools/package.sh 清空 data/*（"交付包零残留"不变量）——随包预初始化必须破坏该不变量，为省一次 9 秒（实测）的 initdb 动打包核心设计，代价错位。initdb 产物不含机器身份（无主机名/绝对路径入 catalog），集群可搬迁是 PG 官方语义；机器一致性由 -E UTF8 --locale=C 给出。妻子场景：首次启动体感路径（欢迎页/聊天/报表）零消费者不经过 PG，initdb 在 pc 编排下与其余进程并发，9-30s 延迟架构上不可见。data/pg 定位：删 data/pg=重置 PG，删 forge=完全卸载。40MB 空集群不进每日备份（forge-backup 白名单制天然不扫；阶段二按 pg_dump 导出物另议）。

## 3. 端口与配置
- 端口：对齐现有 Pick-Port/data/*.port 机制。bootstrap.ps1 以 base 5432 拾取，写 data/pg.port；两个启动器（启动数字员工.cmd、forge/conf/dev-stack-up.ps1）各加一行读入 PG_PORT；process-compose.yaml 用 ${PG_PORT}（faucet 同款）。固定端口会把"目标机恰好装了 PG"变成永久故障类。探活用 pg_ctl status（读 postmaster.pid，不依赖端口），ports.env.yaml overlay 无需扩展。
- 监听面：命令行显式 -c listen_addresses=127.0.0.1（配置即命令、可断言）。认证 -A trust：与 bridge :8790 无鉴权家族姿态一致，loopback 锁定是安全边界；阶段二引入消费者时复核。
- max_connections=20（默认 100 为多客户端设计；每连接一个 backend 进程，收窄 EDR/内存面）。其余参数零实证不盲调。
- 日志：pc per-process log_location: data/logs/pg.log（daily-backup 先例）——pg 重启/恢复噪音不进 pc.log，不挤占报告 256KB 预算。
- 报告 v2 不加 PG 探活行：四条门槛第②条一票否（阶段一零消费者，该行排除不掉任何用户可见故障）。

## 4. 失败面：PG 失败 = 栈照常绿
- 全仓零依赖指向 pg：chat-bridge 0 处 pg/postgres 引用，pc yaml 0 个 depends_on 指向 pg/pg-init。阶段一桥对 PG 的正确依赖数是 0。
- pg 失败只影响自己面板状态；证据自然落 pg.log/pc.log。栈验收线照常绿。
- 重启策略：首选 restart on_failure（与 nats/faucet 一致），前提核实 pc v1.122 支持 max_retries/backoff_seconds（不支持则降级 restart no）——EDR 硬拦时无上限重启循环=白烧 CPU+持续刺激扫描器，零消费者阶段没有对价。阶段二随首个消费者复核翻转。

## 5. 启动脚本面：pc 编排的一次性 pg-init 进程
- 形态：conf/templates/pg-init.tpl.cmd（新模板 ~6 行，__FORGE_ROOT__ 占位）→ bootstrap.ps1 生成 bin/pg-init.cmd（沿用 memory-mcp/forge-backup 生成模式，bootstrap 增 2 行）。pc 新增两进程：
  - pg-init：is_daemon false，restart no，command=生成的 pg-init.cmd。幂等守卫：if exist "%FORGE_ROOT%\data\pg\PG_VERSION" exit /b 0，否则 initdb（-D data/pg -E UTF8 --locale=C -A trust -U postgres，全绝对路径）。-U postgres 使超级用户名确定化。
  - pg：is_daemon true，depends_on { pg-init: process_completed_successfully }（faucet-rawsql→daily-backup 同款原语）；command = bin/pg/bin/postgres.exe -D data/pg -p ${PG_PORT} -c listen_addresses=127.0.0.1 -c max_connections=20（postgres 直接作为 pc 子进程，不经 pg_ctl start，保证 stop/restart 语义完整）。
- 为什么不是 bootstrap 同步 initdb：进首次启动关键路径（双击后静默等 9-30s）+ initdb 失败打断整栈——违反"PG 失败=栈照常绿"。
- 为什么不是 pc 启动命令内联包装：postgres 沦为 cmd 孙进程，pc 杀 cmd 不杀 postgres，孤儿进程面扩大。
- 失败人话：pg-init 失败妻子不可见；脚本内 echo 一行大白话进日志（如"数据仓库准备失败，详见 data\logs\pg.log"），不弹窗不中断。

## 6. 升级面：阶段一锁死"升级 = 删 data/pg 重建"
失效时点写死：阶段二首个消费者写入第一行业务数据的同一个提交里，本策略失效，必须切换 pg_dump/pg_restore 导出先行路径；同批复核 trust 认证/max_connections/备份面/pg_dump 来源。
边界预警（今日实锤）：zonky 与 npm 渠道 repack 都没有 pg_dump（只有 initdb/pg_ctl/postgres 三 exe）。阶段二动工前必须先解决 pg_dump 来源（EDB zip 或第三方 pinned 产物），现在记档不决策。

## 7. pf-engineer 验收清单（全部可断言）
A. 渠道与四件套
1. tools/components.yaml 新增 postgresql 条目（version 17.11.0，maven central jar 精确 URL）；tools/fetch.sh 三步接入（curl jar 走 $PROXY → unzip 取 txz → tar -xJf 解到 forge/bin/pg，顶层 bin/lib/share）。
2. fetch.sh 生成 forge/vendor-licenses/postgresql.PostgreSQL（源 postgres/postgres 仓库 COPYRIGHT，取 REL_17_11 tag），非空断言。
3. tools/package.sh 许可证清单增一行 [postgresql.PostgreSQL]=...，沿用 MISS 即失败机制。
4. tools/checksums.txt 含 bin/pg 三 exe 行（现有 find 逻辑自动纳入，grep 断言）。
5. bin/pg/bin 恰好 3 个 exe；多出任何 exe = 渠道污染，断言报错。
B. pc 编排（dev 栈）
6. process-compose.yaml 新增 pg-init + pg；dev-stack-up.ps1 拉起后 GET /processes：pg Running+healthy，pg-init Done。
7. readiness_probe = exec pg_ctl -D <绝对路径> status，period 5s / threshold 12。
8. bootstrap.ps1：Pick-Port base 5432 写 data/pg.port；生成 bin/pg-init.cmd。幂等：二次拉栈不重建 data/pg。
9. netstat 断言：pg 端口 LISTENING 且绑定 127.0.0.1；data/pg.port 与实际一致；postgresql.conf lc_collate=C、encoding=UTF8。
10. 两个启动器均导出 PG_PORT。
C. 失败面
11. grep 断言：chat-bridge 模板与生成物 0 处 pg/postgres；pc yaml 0 个 depends_on 指向 pg/pg-init。
12. pc 能力核实结论落 yaml 注释：支持 max_retries/backoff → on_failure+max_retries:3+backoff_seconds:5；不支持 → restart no。实测杀 postgres.exe：行为符合所选分支，其余进程不受影响。
13. 人工一轮：占住 pg 端口拉栈 → pg 不健康、栈其余全绿、日志有证据，留痕。
D. 报告/卸载/回归不破坏
14. 落盘诊断报告 grep 0 命中：pg / postgres / 数据仓库。
15. e2e 35/35 + fuzz 44/44 全绿。
16. 停止数字员工.cmd → tasklist 无 postgres.exe；删 data/pg 后重启栈能重建。
E. 实测数据落档（research/10 UNVERIFIED 清账）
17. initdb 耗时两口径：dev 栈一次 + 沙盒 C:\PocketForge-Test 全新部署一次（参考值 9.0s）。
18. PG 空闲内存：tasklist postgres.exe 工作集落档。
19. 包体增量：package.sh 产物前后 diff 落 STATE。
20. 沙盒一轮全流程：新包解压 → 双击启动 → pg Ready → 重启幂等 → 停止卸载断言 → 报告无 PG 字节。
F. 最小 diff 自检
21. 改动面上限：components.yaml / fetch.sh / package.sh（一行）/ bootstrap.ps1（~8 行）/ pg-init.tpl.cmd（新 ~6 行）/ process-compose.yaml（两进程 ~20 行）/ 两个启动器（各一行）/ 生成物。零 bridge 改动、零 UI 改动、零 e2e 框架改动（可加断言节）。
