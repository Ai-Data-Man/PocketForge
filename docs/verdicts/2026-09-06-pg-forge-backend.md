# 裁决书：PG 作为 forge 本身后端——桥状态存储层与切片路线

- 日期：2026-09-06 / 决策人：pf-pm
- 输入源：**用户 2026-09-06 原话：「始终没考虑用已经引入的pg，来作为forge本身的后端或者前后端一体化设施，也完全未对需求做任何回应」**（点名=第一输入源，本指令推翻 pf-pm 此前相关裁决，见 §6）
- 结论：方向采纳。落地形态=桥内「状态存储层」（PG 主、文件回落、lazy ≤2s），切片 1 今天可做（存储层+健康接线+usage 统计首迁）；配置/密钥/组件私有/文件原生状态明确不迁（§8）
- 关联：ADR-0011、裁决 2026-09-05-pg-phase1、2026-09-05-pg-phase2（doctrine 与阶段三门槛出处）、2026-09-05-marketplace-ecosystem §4-S5（被推翻）、research/10、ADR-0009、STATE s66/s69 遗留行

## 0. 本次裁决的性质

用户指令推翻的是**边界裁决**（「桥状态不入 PG」这条线），不是推翻任何工程事实。s66 阶段二裁决把迁移收窄为零消费者的依据（scale-inventory：妻子量级 LIKE 毫秒级、无规模痛点）今天仍然成立——用户推翻的不是这些数据，而是「数据不痛所以不做」这个结论本身：用户要的是**架构方向**（已引入的 PG 必须成为 forge 本身的后端设施），这是产品所有者对架构一致性的意志，不以规模痛点为前提。本裁决的任务是把方向翻译成正确的落地方式，不为旧裁决辩护。

同时记录一个事实勘正：ADR-0011 阶段二字面原文是「forge 自建应用（**chat-bridge 及后续自建应用**）的新增结构化存储默认 PG」——chat-bridge 本就在阶段二范围内。s66 裁决将其收窄为零消费者属执行层再收窄；用户指令把范围拨回 ADR-0011 字面并要求实质落地。

## 1. 问题陈述

- **谁在什么场景下痛**：用户（技术内测者+产品所有者）在审视交付树时：PG 已进树（+36.1MB 压缩、postmaster 多进程运维面、initdb/pg 两进程编排）但全仓零消费者——成本已付、价值为零，且第二次点名（2026-09-04 立项 PG、2026-09-06 指责未回应）说明这是持续预期落空。同时在工程侧，桥自有状态以整文件 JSON 重写方式增长：usage 统计在 WS 消息热路径上写盘（s61 响应性#7 已因此出过真实缺陷家族，改为防抖异步），workspace-map/归档索引随会话数只增不减、每次变更整文件重写。
- **不解决的代价**：①体积与运维成本持续无对价；②每个新状态继续再造一个 JSON 文件+独立迁移管线，长期变更成本斜率向上；③「forge 有正经后端」的架构预期第三次落空即信任损伤。
- **三问**：
  - 用户何时遇到？每次看包体/进程面板/状态文件膨胀时；审查架构时。频率=低频高权重（架构级关切）。
  - 不用它怎么死磕？继续文件管线——能工作，但热路径整写、无事务、无查询能力、每个消费者自写回落逻辑，且 125MB 设施持续白载。
  - 做错的代价？最重=把启动关键路径接到 PG 上，「一次双击启动」验收线崩；次重=把 secrets/组件私有存储卷进来，安全与零二开红线破。本裁决全部结构都为防这两条。

## 2. 归约：「forge 本身的后端」到底是什么

三次为什么：

1. **为什么要求 PG 做 forge 的后端？** → 表层是「引入了就该用」。
2. **为什么「该用」成立？** → 因为 ADR-0011 承诺的就是这个（自建应用首选库，chat-bridge 点名在列），用户批准扩列许可证是为此付了对价（白名单+体积+运维面）；设施无消费者=带部署时间戳的浪费，这正是 pf-pm 自己的纪律。s66 收窄在「数据不痛」上是对的，在「方向可以无限期空转」上是错的——正确形态不是永远空转，也不是一次性大迁移，而是**把存储层立起来，让增长型状态从今天起进 PG**。
3. **为什么是现在、是这个形态？** → 因为桥状态里真实存在 PG 赢过文件的状态家族（§3 Tier A/B）：高写入频率整写（usage）、无界增长整写（workspace-map/归档索引）、以及阶段三消息同步将来必需的事务与删除传播底座。存储层先立，这三类按风险排序逐片进，每片失败面闭合。

**归约结论：「forge 本身的后端」= 桥（chat-bridge）作为前后端一体化产品中的后端进程，其自有结构化状态经统一存储层以 PG 为主存储；文件回落是永久架构不是过渡态。** 不是：引入 Web 框架/独立 API 层/多用户服务化（桥已是后端，缺的是它的数据库）；不是迁移 goose/faucet；不是替妻子自建应用建库（那条轨已有 doctrine）。

## 4. 架构裁决：桥状态存储层

一个桥内模块（唯一 PG 触点），两后端同接口（PgStore/FileStore），按状态逐个绑定：

- **真相源规则**：每状态任一时刻只有一个真相源。PG 可达=PG 真相；PG 不可达=回落文件真相。读路径永不阻塞在 PG 上（内存缓存承载读，启动时从当期真相源加载）；写走真相源。
- **模式机**：`off → connecting → pg | file`，后台定时重探（30s 量级，unref）。file 态期间文件是唯一真相，PG 恢复后**整体 upsert 回迁再切 pg 态**（file 态期间文件必然不旧于 PG，覆盖方向确定，无合并冲突面）。
- **回落快照语义按状态声明**（doctrine ④ 失败面闭合集的逐状态实例化）：正确性状态（归档索引/workspace-map）=每次变更 write-through 文件快照，回落无损；容损状态（usage）=关停/周期快照，回落有损且人话声明。
- **doctrine 全量映射**：新存储默认 PG（①）→ forge_bridge 库（doctrine 命名 forge_<app>，bridge 即第一个 app）；三件套同提交（②）→ postgres.js vendored + schema_migrations 注册表 + psql 恢复工具，切片 1 一次交齐；导出先行（③）→ 迁移 apply 前 pg_dump + forge-backup 链扩 forge_bridge 库；失败面闭合（④）→ 上述模式机+逐状态声明；PG schema 纪律（⑤）→ 每库 schema_migrations 表+代码侧有序 MIGRATIONS，forward-only、幂等、事务包裹、库版本新于代码即拒写+warning。
- **不变量修订**（对 phase-2 §6）：「yaml 桥零 depends_on 指向 pg/pg-init」**保留为硬线**（启动独立性的编排保证）；「桥零 pg/postgres 引用」**废止**（桥自此是合法消费者），替代不变量=「PG 触点收敛在存储层单模块，桥其余代码不见连接串」。
- 报告 v2 维持零 PG 节（可观测性由管理面板承接）；phase-1 验收 14「报告 0 PG 字节」条款随「零消费者」前提消失一并废止，但本切片仍不加报告行。

## 5. 「前后端一体化」的解释与边界

- **解释**：桥=后端（单 node 进程，HTTP+WS），chat.tpl.html=它伺服的前端，PG=后端自有数据库。「一体化」=三者同住一棵便携树、一次双击、无独立服务层——不是引入新框架/新进程/服务器化。
- **与妻子自建应用（阶段二每应用一库）的关系**：平行不混。bridge 用 forge_bridge；妻子应用各得 forge_<app>，禁跨应用共享写（doctrine ① 原文）。存储层是 forge_bridge 的实现，同时是后续每个自建应用存储层的**参考实现**——这才是「一体化设施」的完整含义：不只桥用，而是立下 forge 自建后端的标准形态。
- **启动关键路径论证（为什么一批文件永远留文件）**：时序事实——双击 → bootstrap → pc 并发拉起全进程；pg-init 冷启 12.6s（pc 口径，s66 实测）→ pg 启动 → TCP 探活最长约 60s 判定窗；而 chat-bridge 零 depends_on 秒级起、healthz 即栈绿。**在时间轴上「桥可用」恒早于「PG 可用」**，且 pg 有 crash-loop 实锤家族（管理员令牌拒启、EDR 待验证、端口占用）。推论：凡在 PG 可用前（或永不在场时）被消费的状态，真相必须留文件——secrets.env、providers.json、data/config/*、升级通道、端口文件、VERSION、bootstrap 种子模板。验收线双态化：**PG 不在场=产品完整可用（回落文件态）；PG 在场=状态入 PG。两态都必须可断言。**

## 7. 切片序列（一次会话一片；回归线=e2e 46/46 + fuzz 102/102 不降线）

### 切片 1（今天可做）：存储层骨架 + PG 健康接线 + usage 统计首迁

选 usage 打样的理由：容损声明现成（失败面闭合最容易）、热路径收益最真实、贴现有数据形状（按日 jsonb 一行）diff 最小。**本切片交付的不是一条数据，是「forge 本身后端」的立轨。**

改什么：

- vendored：forge/bin/vendor/pgstore/node_modules/postgres@3.4.9（沿 artifact-vcs 先例）+ vendor-licenses 条目（Unlicense）。
- psql.exe 进 bin/pg/bin（EDB zip 同源 pin -1，fetch.sh 抽取+闭包断言，复用 pg_dump 先例）——三件套 doctrine ② 的恢复工具，随首行业务数据同提交。
- 桥内存储层单模块：lazy 连接（connect_timeout ≤2s）、模式机、30s 后台重探、forge_bridge 的 schema_migrations 注册表+MIGRATIONS v1（usage_daily(date pk, payload jsonb, updated_at)）、apply 前 pg_dump、库版本倒挂拒写。
- usage 切换：statsBump 沿用 2s 防抖批量 UPSERT；重启恢复真相源改 PG；存量 data/stats/usage-*.json 幂等导入（按 date upsert）；file 态行为与今天逐位一致。
- forge-backup 增 forge_bridge 库 dump（phase-2 §2「多库枚举随三件套」兑付，防「备份链只护空库」的假保护）。
- 管理面板「数据存储」人话块（两态：「数据库正常 PostgreSQL / 已回落本地文件+原因大白话」）+ stateWarnings 增 PG 条目；/healthz 语义不变（恒 200，探活职责在 pc）。

验收标准（工程师直接执行）：

1. vendor 三验：require 可用、package.sh 许可证断言过、checksums 覆盖 vendor 与 psql.exe。
2. 恢复演练留痕：pg_dump forge_bridge → 重建库 → psql 导入 → 行数逐表一致（tmp 留痕）。
3. 连接纪律断言：不可路由地址实测 connect 超时 ≤2s（research/10 已证 2004ms 语义，复测入 fuzz）。
4. 四态失败面（e2e 新节或 fuzz 全覆盖，每态断言 healthz 200+聊天冒烟过+面板人话正确）：pg 不在场（data/pg 改名模拟）；pg 进程被杀；端口黑洞（超时路径）；迁移失败注入（该状态回落文件+warning，桥不崩）。
5. 双态冷启（沙盒，runas 降权包装沿 s67 先例）：PG 在场=usage 入 forge_bridge、当日文件停止增长（仅快照）；PG 不在场=双击启动全功能绿、面板回落人话。启动→healthz 时延相对基线漂移 <10%。
6. 备份：PG 在场跑 forge-backup → zip 内含 forge_bridge dump 且行数>0；PG 不在场 → backup.log warn、zip 照常（既有行为不回归）。
7. 升级路径一轮：v0.9.10 → dev 树升级，PROTECTED 'data/' 覆盖 data/pg 与 vendor 语义复核，升级后 usage 历史完好。

## 8. 明确不迁清单（防重新谈判）

1. **providers.json 与 secrets.env**——安全取舍论证（§3-#4）：威胁模型不变（loopback trust 下本机进程对 PG/文件权限等价）、启动关键性决定双真相源代价、pg_dump 会把明文 key 扩散进每日备份、技术用户手-edit 恢复面是内测期资产。迁移的唯一想象收益（「数据库更安全」）在当前认证形态下为零。若未来上 SCRAM/角色加固，本条可随安全裁决重开——不是现在。
2. **data/config/*（skill-sources/mcp-catalog）**——用户手-edit 配置面，s69 刚交付的设计即「加源=编辑文件」。
3. **升级通道（data/update.json、data/updates/*）**——恢复路径不得依赖被恢复对象；status.json 存在跨进程双写方（detached runner）。
4. **缓存类（data/cache/skills/manifest.json）**——派生数据，文件是缓存的正确载体。
5. **文件原生类**——origin.json、.forge、reports、memory/*.txt、*.port、welcome 标记、backups：与目录同生命周期或属基础设施标记。
6. **禁迁类（零二开红线）**——goose sessions.db/schedule.json/conf/goose/**、faucet 库。本裁决与后续任何切片不得触碰。
7. **永久架构线**——yaml 桥零 depends_on 指向 pg/pg-init；桥启动永不等待 PG；文件回落态是永久支持的运行模式，不是迁移期的脚手架。任何「PG 在场则文件只读化/移除回落」的提案都违反双态验收线，视为违反本裁决。
