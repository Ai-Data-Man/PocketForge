## 2. 根因归约（三次为什么；区分事实/假设）

### 症状 1：拥挤（技能弹窗堆叠、归档埋底）

- 为什么拥挤是问题？→ 管理成本随规模非线性增长：42 条市场+十几条已装同滚，找一条要滚+翻页交叉；归档入口随活跃列表变长而沉降。
- 为什么会长成这样？→ 每个清单做出来时规模小（当时够用），增长后没有触发形态升级的机制——分页是用户点名第三次（s73）才补的，搜索至今没补到已启用区。
- 为什么没有形态升级机制？→ **【事实】不存在「清单规模预期声明」这一设计步骤**：代码里没有任何地方回答「这个清单最多会有多少条、超了怎么办」。形态是按当时条数选的，不是按终态选的。

### 症状 2：错位（技能源在插件页）

- 为什么错？→ 技能源决定技能市场的进货，与「插件」无用户心智关联；市场本体在 🧩 弹窗，进货配置在 🔌 标签，隔着两个入口。
- 为什么当时放那？→ 【事实，s73 1c9aad7】当时要推翻「源配置无入口」的批评，就近塞进了技术语义最接近的面板——按**实现方便**放置，不是按**使用域归属**放置。
- 为什么会按实现方便放？→ **缺「配置归属规则」**：没有一条判据说「配置必须住在它所配置的东西的使用域里」，于是任何新配置块都往「最近的相关容器」堆。

### 症状 3：无解释（表名裸奔）

- 为什么没解释？→ 表是 faucet 应用动态建的（c20260901_xxx 型命名），系统里不存在「表说明」这个数据；列级人话（s51）有 _schema 原料所以做了，表级没有原料。
- 为什么没有原料？→ 建表的是小 forge（agent），它建表时知道意图，但没人要求它留下说明。
- 为什么没人要求？→ **缺「机器生成物必须自带人话身份」的义务规则**——解释层被当成 UI 装修（有原料才显示），而不是资产创建时的数据义务。表多了没有信息架构承托（用户原话预判了 1/2 的老路），根子同源。

### 归约结论（制度缺失，非点位缺失）

四个症状归约到**一条基本要素：UI 按「功能实现顺序」生长，而非按「信息架构」设计**。具体缺四样东西，合成本规范 R1–R4：

1. 信息域定义（一容器管什么实体、规模预算多大）——缺它 → 同页堆叠（症状 1）与跨域塞放（症状 2）。
2. 列表规模阶梯（多少条换什么形态的量化阈值）——缺它 → 点名一次补一次（症状 1）。
3. 配置归属规则（配置跟随使用域）——缺它 → 技能源进插件页（症状 2）。
4. 解释层义务（动态资产建时落人话身份）——缺它 → 表名裸奔且规模越大越糟（症状 3）。

【假设标注】妻子认知负荷阈值（下文 7±2、一屏比较）取自通用 HCI 常识而非本项目实测；「技能弹窗=妻子高频、管理面板=低频」来自产品设计意图（fnote 自述「它是什么样、会什么、记了什么、几点干活——都在这里」chat.tpl.html:378），s49 使用统计本次未取数佐证。两处假设不改变裁决方向，仅影响阈值松紧。

## 3. 规模安全信息架构规范（doctrine，qa 可执行检查单）

**R1 同页堆叠边界：一容器一实体，一视图一动作阶段**

- 一个 modal/标签页 = 一个信息域 = 管理一类实体。两类实体（技能 vs 插件）禁止同容器。
- 同一实体的不同生命周期阶段（已装 vs 可装）可同容器，但必须用显式 tab/分区切换，禁止滚动串接两个阶段各自可滚的长清单。
- 每个视图 ≤1 个主清单区块；说明性 h3/fnote 不算区块。
- 【检查】这个容器里有几类实体？>1 → 拆。两个区块是同实体的不同阶段吗？是 → tab 化；否 → 分家。

**R2 列表规模阶梯：形态由规模预期决定，不由当前条数决定**

- 0–8 条：直接列，零机制。理由：一眼可扫描（7±2 工作记忆），任何机制都是噪音。
- 9–30 条：直接列 + 必须有搜索。理由：约三屏滚动内可浏览，但条目名不可预测时小白唯一自助找回手段是搜索。
- 31–100 条：分页（卡片型 PAGE_N=12 / 行型 30，复用 pageSlice）+ 搜索。
- >100 条或天然多主：先分组（按实体归属，如按应用分库），组内再走本阶梯。
- 优先序：搜索 > 分组 > 分页——搜索帮「定位」，分组帮「理解结构」，分页只防「渲染挤压」，后两者不替代前者。
- **任何上限截断必须留替代出路**（搜索/过滤/完整视图），无出路的截断禁止上线（现状违规项：活跃 40 截断有搜索兜底 ✅、归档 30 截断无搜索 ❌ IA-2 修、db 50 截断无搜索 ❌ IA-3 修）。
- 【检查】新清单提交必须声明规模预期（终态最多多少条）；预期 >30 无搜索、>100 无分组 = 审查不过。

**R3 配置归属：配置跟随使用域，按「改了它去哪看效果」归类**

- 归属判据一句话：这个配置改了之后，用户会去**哪个界面**看效果——配置就放那个界面（或其内部的收起技术区）。
- 禁止按技术相似性聚类（「都是源配置所以放一起」= 症状 2 的病根）。
- 高频使用域（妻子的主路径：技能弹窗、侧栏、聊天区）不放裸露技术配置；技术配置允许同域但必须折叠收起、默认不可见——「同域不同层」。
- 【检查】每个配置块问一遍归属问题；答案指向的界面 ≠ 所在界面 → 搬家。

**R4 解释层义务：面向妻子的清单，条目必须有人话身份**

- 面向妻子的任何清单，条目主名非中文人话（英文表名/包名/命令名）时，必须附一行人话解释；无解释不得上线。
- 解释来源优先级：① 系统元数据（创建时落的说明，唯一可靠源）② 结构性事实（列数、类型、样例值——可自动生成，但**不得编造用途**）③ 无解释时显示来源+创建时间等自动元数据占位，禁止空白。
- 机器/agent 生成的资产（表、应用）在人话身份上是**数据管线义务**（建时落元数据），UI 只消费——UI 端猜用途=误导小白，比没有更糟。
- 【检查】逐条目问：这个解释从哪来（元数据/结构推断/占位）？来源答不出的条目不许出现在妻子界面。

## 6. 表名解释数据来源裁决 + 分组裁决

| 候选 | 裁决 | 理由 |
|---|---|---|
| a) 建表时 faucet 落备注 | **否决** | faucet 零二开（ADR-0006）；且 faucet schema 通道未见表级 comment 字段（chat-bridge.tpl.js:1306-1310，【假设：未穷举 faucet CLI 全输出】）。查证+改造双成本，收益与 d 重合 |
| b) 桥端静态映射 | **否决（主体）/ 保留一格** | 表由 agent 持续动态建，逐表手写不可持续（用户原话预判的「老路」）。唯一保留：桥自建的固定系统表可随代码预写说明（数量恒定、随版本走，不是「映射表」是常量） |
| c) _schema 列级人话+首行推断 | **降级层采纳 / 推断否决** | 列级人话已有（s51）作无说明时的降级展示；但从列名/样例**编造表用途**对小白是误导（比空白更糟，违反 R4 ①②边界）——结构性事实（几列、样例）可自动展示，用途句禁止生成 |
| d) agent 建表写说明入 forge_table_info | **主路径采纳** | 建表者=唯一知道意图的一方（小 forge）；落库为元数据=单一真相源、随表生命周期走；桥只消费不做猜测。软约束（提示词约定）而非机制强制——强制需拦建表通道，faucet 零二开下做不到；漏写降级 c 占位，不阻断 |

分组裁决：**按 service（faucet 应用分库）分组**。理由：分组边界是数据本来的物理边界（一应用一库，ADR-0011 阶段二 doctrine），零映射成本；组内条数天然少（单应用表数个位~十位数），组内直接列即可（R2 阶梯在组内通常停在 0–8 档）；搜索做跨组定位。否决「按时间/按行数」等二次分组维度——无用户任务支撑，纯设计者想象。

## 7. 明确否决项（防重新谈判 / 防过度设计）

1. **虚拟列表/无限滚动等重前端机制**——否决。最大现实清单 158 条行型，pageSlice 切片渲染毫无压力；为假设的万级规模造机制违反验证优先。
2. **引入组件库/新依赖/新 CSS 框架**——否决。rtab/pageSlice/pagerPaint/防抖搜索全部现成，本裁决所有切片复用既有机制，不造新轮子。
3. **管理面板加第七标签**——否决。六标签是认知上限；新需求先过 R3 归属判据，归属不明的需求退回重问。
4. **UI 端智能推断表用途（LLM 生成说明）**——否决。见 §6-c：编造用途误导小白；且给静态清单挂生成链路=引入失败面。
5. **把技术配置做出「妻子可见的源管理界面」**——否决。沿 marketplace-ecosystem 裁决第 4 条：源=技术配置，折叠收起；妻子扩展能力的入口是「装技能」，不是「加源」。
6. **一步到位重构全部存量清单**——否决。ext/sched/model-pool/prov-list 现规模全部合规（0–8 档），只落声明+触发器（IA-4），不动代码。点名批评的三个域修完即止——最小 diff 纪律。
7. **归档视图加筛选器（按时间/按应用）**——否决。无任务证据；搜索+分页已满足「找回」；触发器=妻子实测反馈找不回再加。

## 8. 非目标

- 不动妻子聊天主流程与顶栏；不动 ⚙️ 服务商面板（归属正确）；不动 goose/faucet 内部（零二开）；不做数据表内容编辑/导出（只有查看，现状语义不变）；不迁移归档数据存储形态（PG 切片 3 另议）；本裁决只约束 UI 信息架构与表说明元数据，不触碰 PG 阶段边界（forge_table_info 入 forge_bridge 库属桥状态管线，ADR-0009 schema 纪律管辖，与阶段二「应用数据」边界不冲突）。

## 9. 成功指标与观察窗口

- 结构：技能弹窗打开后单视图内不出现两类清单；归档入口「打开侧栏即见」不依赖滚动；数据面板每个应用表行有一句说明或明确占位。
- 回归：e2e-chat/fuzz 全绿不降线；s70/s71/s73 既有功能（来源徽标/分页/源持久化）实景不回归。
- 机制生效（观察窗 2 周）：新表经 agent 约定带说明的比例（目标：护航期建表 100% 带，漏写可见占位但不误导）；qa 能用 R1–R4 检查单拦截至少一次「无规模声明的新清单」（第一次拦截=制度活了的证据）。
- 下一轮输入：妻子真机反馈——归档找回是否还困难、技能弹窗双 tab 是否可自主切换、表说明是否被阅读。若妻子从不看表说明，IA-3 的 agent 约定维持但 UI 展示降级为点开态（R4 合规前提下再熵减）。
