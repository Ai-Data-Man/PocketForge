## 1. 归约与三问

三次为什么：
1. 为什么做机制？→ 改配方后不传导，定时任务继续按旧设置无人值守地跑。
2. 为什么这是护航期真实风险而非完美主义？→ ①漂移不是假设，当下实态就是（§0 第 2 行）；②定时任务是妻子核心场景（s55 用户点名暂停/恢复）；③s14 事故证明「改定时任务」路径在产品内真实发生过且代价最重；④静默性——漂移不报任何错，妻子/agent/我们都不可能自然发现。
3. 为什么是「告警」而不是「自动修」？→ **不传导 vs 改错传导哪个更伤：本产品语境下不传导更伤**——不传导是静默的（跑旧行为、无报错、可复活无熔断副本=goose-guardrails §0 排序第一的「无人值守+无上限」组合）；改错传导至少下次运行可见可查。而自动传导是「改错传导的自动化版」：错误改动会在无人看屏的时点立即生效。故方向定为**把漂移变成可见**，永不自动改。

三问回答：
- **用户何时遇到？** 妻子说「把那个任务改一下」（→agent，目前无协议可循）；或我们护航期调配方（s69 G4 同款，已发生 1 次）；或任何人点 ▶ 复活陈旧副本（当下可触发）。
- **不用它怎么死磕？** 手工 diff 两个 yaml——妻子零可能，agent 无理由自发做，我们靠记性。死磕成本=静默事故。
- **做错的代价？** 只读告警最坏情形=误报打扰（一次多余确认），无破坏面；自动/按钮方案的代价见 §2。

## 2. 候选裁决

### 候选 c（只读对账告警）：✅ 做——本轮主体
- **机制**：GET /api/schedules 逐条对账——以 `recipe_base_dir`+副本文件名找源配方；找不到再按 title 匹配目录内配方（两文件 title 同为「每日记忆自检」，实测可通）；找到且**内容不等**→ 返回 `drift:true`。UI 在该任务行下加一行人话：「设置改过，改动还没生效。在聊天里跟它说“把〈任务名〉重新登记一下”就好。」
- **为什么它够**：告警文案给出零技术用户可执行的出口（说一句话），出口的执行者是有手册协议的 agent（§S3 补上后）。可见性闭合，操作面零新增。
- **失败面**：①映射歧义（多配方同 title）→ 裁决=歧义时不告警（宁可漏报不可误报，漏报兜底仍是手册铁律）；②goose add 时若规范化副本内容（重排键序）→ 内容比对恒不等=常驻误报——**验收项 2 专测此点**（重登记后立即复查 drift 必须为 false；若 goose 确实规范化，降级为逐行语义比对，工程师现场定）；③源配方被删 → 不告警（任务本身是活体，源没了不算漂移）。
- **diff 量级**：桥 ~15 行（readTitle 挂点旁）+ UI ~8 行。无新端点、无新 POST op、无子进程。

### 候选 a（告警+一键重新登记按钮）：⚠️ 挂起——按钮部分待触发器
- 按钮链=remove → add（同 id、保 cron、--recipe-source）→ `pc process restart goose-scheduler`，若原任务是 paused 还需第 4 步补 pause（CLI 无 pause 子命令，s55 实证；re-add 会使 PAUSED→ACTIVE）。
- **失败面盘点**：任务运行中点按钮（remove 对 running 任务行为未知）；链中断在 remove 之后=任务被删（比陈旧更糟）；title 歧义时按钮指向错误配方；paused 态静默翻转。四个失败面 × 零观测的妻子侧修改频率，diff/风险与收益不成比例。
- 触发器见 §4。

### 候选 b（自动传导）：⛔ 否决
1. 无人看屏时点自动改任务且 PAUSED→ACTIVE 静默翻转——违背「重要操作问用户」产品语义（G1 同精神，goose-guardrails §0 取舍主轴）。
2. 与守护竞态实锤：sync_from_storage 只按 id 增删不更新（s55 VERIFIED-RUN）；remove/add/restart 多步链自动化的每一步失败模式都是「任务没了」或「改了个寂寞」。
3. 频率为零的妻子侧事件不配自动化——自动化解高频烦扰，不解零频边角。
4. 陈旧副本风险由告警+resume 确认（S2b）覆盖，不需要隐形魔法。

### 代码核后新增候选（任务书授权增删）
- **S2b 漂移态 ▶ 恢复确认**（新增，~3 行）：`j.drift && j.paused` 时点 ▶ 先 confirm（引用同句人话），无漂移任务行为零变化。理由：▶ 是陈旧副本（含无熔断版）唯一的复活入口，告警牌就竖在触发按钮旁边却不拦一下，等于立牌不设卡。这是 c 的必要补全，非范围蔓延。

## 3. 切片与验收（pf-engineer 可直接领走）

### S1 桥侧对账（chat-bridge.tpl.js /api/schedules GET）
- 改：GET 分支逐条计算 drift——`recipe_base_dir` 剥 `\\?\` 前缀（实态数据带此前缀）→ `join(baseDir, basename(j.source))` 不存在则目录扫描 title 相等（复用 readTitle）且唯一者；找到且 `readFileSync` 内容 !== 副本内容 → `drift:true`。recipe_base_dir 缺失 / 无匹配 / 多匹配 → `drift:false` 静默。
- 验收：①当前 daily-mem 实态即夹具——GET 返回 drift:true（副本无 max_turns、源有）；②title 匹配路径打通（basename 必失败系实态，见 §0 第 3 行）；③删源配方 → drift 归 false。

### S2 UI 提示行 + resume 确认（chat.tpl.html loadSchedUI）
- 改：行内 fnote 追加告警行（文案见 §2c，零术语审读）；`j.drift && j.paused` 时 ▶ 前置 confirm。
- 验收：①漂移行只在 drift 时出现；②确认对话取消后按钮恢复可点、任务未被 resume；③无漂移任务 ▶ 行为逐位不变（零回归）；④昼夜两主题目视过一遍。

### S3 手册修改协议（goose-hints.tpl.md 定时任务节）
- 改：补「用户要**改**已有任务（改时间/改指令）」协议：①改配方文件 → ②`schedule remove --schedule-id 同一id` → ③`schedule add`（同 id、新 cron、--recipe-source 源配方）→ ④`pc process restart goose-scheduler` → ⑤人话复述，并提醒「重新登记后任务是启用状态；之前是暂停的话，要在面板里再暂停一次」（CLI 无 pause，PAUSED→ACTIVE 不可免）。铁律第三条同步落：**改配方必须重登记，不重登记=改动不生效**。
- 验收：零术语审读；沙盒实景走一遍（daily-mem 重登记后 S1 告警消失=端到端闭环）。

### S4 验证与回归
- 沙盒：S1 验收 1-3 + S3 闭环 + 重登记后立即复查 drift=false（专测 goose 是否规范化副本内容，§2c 失败面②）。
- 回归：e2e-chat 补 GET drift 两态断言；e2e 48/48、fuzz 143/143 不降线；goose 零改动（无 goose 侧文件 diff）。
