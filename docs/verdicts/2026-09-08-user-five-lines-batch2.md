## 2. 主线 1：提示词管理（库+搜索+分页）

### 2.1 归约（三次为什么）

1. **为什么用户说「强化」？** 归约到真任务：用户（和妻子）反复重新输入同类话术——「每周帮我做那张表」「查一下缸体还剩多少」。库的价值=**说一遍就留住我的说法**。搜索+分页是找回手段，不是目的。
2. **「已有提示词」指什么？** 用结果衡量：妻子打开这个库，要看到的是**她的常用话术**，五条十条，一眼可点。历史自动留存（1709 条）混入后她的常用话术被调试噪音淹没——库越全越不可用。**全量留存违背库的存在目的，裁。** 解读 B（手工收藏）为主体；解读 A 的合理内核（从历史收藏）收敛为一个显式动作，不做自动。
3. **为什么用户原话「必须带搜索+分页」？** 他是对的需求方：R2 规范（31-100 档=分页+搜索）与硬核用户终态（个人活跃话术 10-50 条，UNVERIFIED 推断）吻合。用户要的不是小玩具，是**能装下终态的形态**——按 31-100 档实现，规模小则 pagerPaint 自动零机制（tpl:1933），妻子侧 5 条起步零分页噪音，两头兼容。

### 2.2 裁决

1. **语义定案：手工收藏制**。唯一真相源=用户显式保存。入库动作本批两个：a) 输入框当前草稿一键保存（面板内主入口）；c) 面板内手工新建/编辑。b) 已发消息操作条「存为提示词」**本批不做**（挂触发器，见 §8）。
2. **存储**：`data/prompts.json`，条目 `{id, name, body, created_at, updated_at}`（id=桥生成，时间戳 ISO）；readJson+atomicWrite（s15/s75 纪律）；STATE_SCHEMAS 注册 `'prompts.json': {latest:1, steps:{}}`（ADR-0009）。PG 双写镜像（pgStateSync）本批不挂，可后挂。
3. **桥端点**（对齐 /api/memory op 风格，research/22 §4.3）：
   - `GET /api/prompts` → 全量条目（量级小全量返，前端分页）；
   - `POST /api/prompts` → `{op:'add', name?, body}` / `{op:'update', id, name?, body}` / `{op:'delete', id}`，响应 `{ok, err}`。name 缺省=body 首行前 20 字。
   - add/update 刷 updated_at；列表 updated_at 倒序。
4. **UI（R3 定案：使用域=输入框近旁，非管理面板第六 tab）**：`#inputbar` 旁小图标按钮开提示词面板（上弹 popover，形态对齐 @ 菜单容器先例）；面板内=搜索框+行型清单+分页器+「保存当前输入框为提示词」+条目编辑/删除。管理动作同域收进面板（R3 同域不同层，IA-1 技能源 details.tz 折叠先例）。
   - 搜索：前端过滤（lowercase includes，对齐 skills-q），匹配域=name+body。
   - 分页：pageSlice 行型 30/页+pagerPaint；搜索变化回第 1 页（arch-q 先例 tpl:748-749）。
   - 删除=行内二次点击确认（「删除」→「确认删」），无 modal（防误删，妻子侧成本低）。
   - R2 规模声明（落码注释，tpl:722-724 样式）：**终态预期 ≤100 条**（手工收藏制：妻子 ≤30，硬核用户 10-50 为推断上界）→ 落 31-100 档=分页+搜索。
5. **R1-R4 核对**：R1 面板=单一实体（提示词）单清单单区块 ✓；R2 档位声明+机制齐备 ✓；R3 效果出现在输入框（插入即用）→ 归输入框使用域，否决管理面板 tab（技术相似性聚类路线与 R3 文字相悖）✓；R4 条目主名=用户自己起的中文名天然合规，name 缺省兜底=正文前 20 字（结构性事实，不编造）✓。

### 2.3 明确不做（主线 1）

- **历史全量自动留存**：1709 条里 99% 调试噪音；sessions.db 归 goose 自迁移永不手改（AGENTS.md §3.5），只读抽取也只会造出垃圾场。裁。
- **QUICK_PROMPTS 5 条种子入库**：欢迎页 chips 已是它的位置（tpl:752-758），复制进库=双入口状态分叉。库从 0 起步。裁。
- **管理面板第六 tab / 技能弹窗塞提示词 tab**：前者违反 R3（效果在输入框）+s76 刚六减五的结构反复；后者违反 R1（技能=它怎么做，提示词=你要它做什么，两类实体）。均裁。
- **标签/文件夹/导入导出/分享**：零证据需求，规模声明 ≤100 条内搜索即找回。裁。
- **服务端搜索**：条目 <几百 前端过滤毫秒级（skills 先例）。裁。

### 2.4 验收标准（主线 1）

1. 探针：add 三条 → GET 返回且 updated_at 倒序；update 改名后 GET 反映；delete 后 GET 缺席；文件 data/prompts.json 存在且 STATE_SCHEMAS 含注册键；重启桥后数据存活。
2. GUI：面板开关/搜索过滤命中（name 与 body 各一例）/翻页（种 >30 条夹具验证 pagerPaint 出现与翻页正确）/删除二次确认两步生效。
3. 输入框草稿保存：txt 有内容 →「保存当前输入框」→ 出现在清单顶部，name=首行前 20 字。
4. 原子性与安全：写过程 tmp+rename（grep atomicWrite 调用）；跨站 POST 被 Origin 拒绝（自动覆盖，抽查一条）。
5. e2e-chat / fuzz 全绿不降线；R2 规模声明注释在码（qa 审查依据）。

## 3. 主线 2：输入框 Tab 唤起提示词搜索

### 3.1 归约

1. **为什么要 Tab？** ② 的价值=不打断输入流：话到嘴边想起「存过这句」→按 Tab→搜→回车，三击内回来。开面板找=离开输入现场，Tab=现场内直达。
2. **为什么菜单内过滤而不是输入框文本做查询？** 输入框常有半句草稿，全文当查询必失配（@ 菜单有 @ 尾缀作协议锚点，Tab 无天然锚点）→ 唤起后**菜单顶部自带迷你过滤框**，输入框文本不动，插入落在光标处。
3. **三菜单怎么共处？** @（文件/表引用）、slash（命令）、Tab（提示词）同挂输入框上弹区，同用 ↑↓/Enter/Esc。并存渲染=「很迷」预约。**互斥：同一时刻至多一个菜单**。

### 3.2 裁决

1. **唤起**：输入框聚焦 && `e.key==='Tab'` && `!e.isComposing` → preventDefault（阻焦点跳走）+唤起菜单。IME 组合态不劫持（Tab 是部分输入法选字翻页键，research/22 §1.4）。菜单已开时再按 Tab=无操作。
2. **菜单形态**（对齐 @ 菜单先例，research/22 §1.5/§2.2）：上弹容器挂 #inputbar；顶部迷你过滤框（自动聚焦）；下方行清单=名称 b+右侧灰注正文前 40 字；**12 条上限+溢出提示**「还有 N 条没列出来，继续输入缩小范围」（R2 出路=主线 1 面板完整搜索+分页）；过滤防抖 180ms+代际守卫（atGen 同款）。
3. **匹配**：slashHits 复用（条目映射 {cmd:name, alias:[name], desc:body前200字}），中文直接可搜。
4. **键盘**：↑↓ 环形移高亮（共用 menuHl）、Enter 选中、Esc 关菜单焦点回输入框——全部带 isComposing 守卫（tpl:2201 同款）。
5. **选中语义=插入不发送**：正文插入输入框光标处+焦点回输入框+光标移到插入文本末尾。**不自动发送**——「取回修改」（batch1 §4）与 QUICK_PROMPTS（tpl:763 点击填入不发送）两条先例的产品一致性。用户要发送，再按一次 Enter。
6. **三菜单互斥规则**：任一时刻至多一个可见。输入协议命中（/ 开头→slash、@ 尾缀→@）自动切换到协议菜单（内容协议优先于手动 Tab 菜单）；Esc 关当前；菜单间不叠层。
7. **与主线 1 关系**：同一数据源（data/prompts.json）同一端点（/api/prompts），前端内存缓存一份+CRUD 后失效重拉（dbOvCache 60s 先例可简化为「拉一次+写后刷新」）。
8. **R1-R4 核对**：R1 三菜单互斥=同容器至多一清单 ✓；R2 输入驱动即时过滤+12 条上限+溢出提示+完整出路（面板）=「@ 引用菜单」同款天然合规 ✓；R3 入口在使用现场 ✓；R4 主名中文名+灰注摘要 ✓。

### 3.3 明确不做（主线 2）

- **选中即发送**：与「取回修改」红线（载入不自动提交）和 QUICK_PROMPTS 先例冲突；误选即烧一次真实调用。裁。发送权永远在 Enter。
- **输入框全文当过滤查询**：半句草稿必失配（§3.1-2）。裁。
- **placeholder 宣传 Tab**：本批不加（placeholder 已宣传 @；Tab 入口的可发现性观察护航期反馈，若妻子侧找不到再议——不加就不是承诺）。
- **菜单内编辑/删除**：管理动作归面板（R3 同域不同层），菜单只消费。裁。

### 3.4 验收标准（主线 2）

1. GUI：聚焦输入框按 Tab 弹菜单；过滤框输入缩小清单；↑↓ 移高亮；Enter=正文插入光标处+焦点回输入框+**未触发发送**（busy 不变、无 ws send 断言）；Esc 关菜单焦点仍在输入框。
2. IME：组合态（isComposing）按 Tab 不劫持（断言守卫分支）；组合态 ↑↓/Esc 不劫持（现状不回归）。
3. 互斥：Tab 菜单开着 → 输入 / 开头 → slash 菜单替换 Tab 菜单（至多一个可见）；@ 尾缀同理。
4. 溢出：种 >12 条夹具 → 第 13 条起显示溢出提示；面板搜索能找到未列出的条目。
5. e2e-chat / fuzz 全绿不降线；新 ui-logic 断言入第 14 节。

## 4. 主线 3：提示词优化按钮

### 4.1 归约

1. **为什么用户点名「吸收外部最佳实践」？** 归约到真任务：他知道自己写的话术离「模型好消化的形态」差在哪（含糊、缺输出格式、范围太宽），要一个**一键把粗话术变规格**的按钮。不是要模板库（Hub 无质量背书教训，research/20 §1.8 裁掉）、不是要数据驱动优化（GEPA 需百次评估，形态不符）。
2. **为什么必须预览不能直接替换？** Cursor 社区实锤：enhance 会「加入用户没写的假设」（research/20 §1.3）——静默替换=用户失去对最终文本的控制权，错误假设随发送进上下文。Augment 把「审查编辑」列为显式产品步骤、OpenAI 用预览+一键应用，两家官方形态一致。**直接替换=已知的失败模式，裁。**
3. **喂什么上下文？** Augment 注入代码库，PocketForge 的对应物=当前对话（任务目标就在对话里，单列「任务目标」字段=过度设计）。输入框原文是主料，对话摘要是佐料（限 ~1500 字防失控）。

### 4.2 裁决

1. **位置形态**：`#inputbar` 内发送钮旁 ✨ 小按钮（与主线 1 面板入口、主线 2 同域——输入框=话术工作域，R3）。空输入框=disabled+title「先写点什么再优化」。
2. **机制**：WS 消息 `{type:'optimize_prompt', text, context, model}`，桥端克隆 explain_tool 骨架（单次直调当前会话模型+流式+reasoning_effort:'none' 400 重试+30s 超时+sha1 缓存+不进会话历史，research/20 §3-A1）。缓存键=全载荷 sha1（text+context 都进键）。
3. **sysP 骨架**（固定变换清单落死，research/20 §3-A3/A4）：
   - 五条变换：①消歧/澄清含糊表述 ②补输出格式（表格/清单/段落/文件）③补长度与受众约束 ④收窄任务范围 ⑤去口语冗余；
   - 硬禁令：**不得新增用户未提出的任务目标、假设或背景**；
   - 输出双段式：`<optimized>改写稿</optimized>` + `<changes>逐条改了什么</changes>`；
   - 语言跟随原文（中文进中文出）；保留原意，不追求华丽。
4. **上下文构造**（前端）：输入框原文全文 + 当前会话最近消息摘要（msgText 提取，role+正文，从最新向前累计 ~1500 字截断）；新会话无上文 → `context:'（新对话，暂无上文）'`，照常优化（OpenAI Optimize=纯提示词自身变换的形态）。
5. **流程=预览-接受-放弃**：点击 → 按钮 loading 态（禁重复点击）→ 输入框上方预览卡（优化稿全文+逐条变更摘要）→「用这版」（替换入输入框，**替换后仍可继续编辑**，发送权在用户）/「不用」（关闭，**原文逐字不动**）。
6. **错位守卫**：结果到达时若输入框文本 ≠ 优化发起时原文 → 预览卡自动关闭+一句提示「输入已变，已放弃本次优化结果」（防错位替换，替代「原文已变还要不要」的过度设计）。
7. **失败行为**：12s 无首字人话错误+可重试（explain 前端兜底先例 tpl:1061-1067）。
8. **与主线 2 联动**：不做优化专用入库钮。「用这版」替换后文本就在输入框 → 主线 1 的「保存当前输入框为提示词」即闭环，零新增 UI。
9. **R1-R4 核对**：R1 预览卡=单一信息域（优化结果），不与输入框草稿混容器 ✓；R3 按钮在使用现场 ✓；R2/R4 不涉清单与资产名。

### 4.3 明确不做（主线 3）

- **直接替换/自动发送优化稿**：Cursor 失败模式（§4.1-2）。裁。
- **澄清问题分流**（research/20 §3-A6）：超短输入返回 2-3 个问题而非改写——好想法但本批不加（新消息形态+频次未证）。挂触发器 §8。
- **模板库**：LangSmith Hub 无质量背书教训；生成式优化（按当前上下文定制）优于静态模板。永久裁。
- **GEPA/DSPy 数据驱动**：需 trainset+metric+百次评估，与单次直调形态根本不符。永久裁。
- **优化专用一键入库**：动作已存在（主线 1 保存），入口不增殖。裁。

### 4.4 验收标准（主线 3）

1. 空输入框按钮 disabled；非空可点。
2. 探针（假内容断言双段式）：返回含 optimized/changes 两段；预览卡渲染优化稿+逐条摘要；「不用」后 txt.value 与原文逐字一致；「用这版」后 txt.value=优化稿且可继续编辑、未发送。
3. 错位守卫：发起后手改输入框 → 结果到达时预览卡不出现+提示语出现。
4. 上下文：新会话首条（无上文）优化成功；带对话历史的会话优化成功（探针抓桥侧收到的 context 非空）。
5. 12s 兜底：假 provider 挂死 → 人话错误+按钮恢复。
6. e2e-chat / fuzz 全绿不降线。

## 5. 主线 4：白话解释工具调用重写（缺陷定性，五线之首）

### 5.1 归约

1. **为什么定性缺陷而非功能？** 交付物验收线明列「工具调用大白话解释 ✅」（STATE.md:69）——P1 断供使该 ✅ 在生产上是假的：解释者从未见过工具输出（F1），9/9 捏造结果（把装好的 git 说成没装=**事实反转**）。验收线失真比功能缺失更重（batch1 §2.1 同款判据）。
2. **为什么用户骂「把想了解技术的用户当傻子」是对的？** Claude Code 社区反弹同构证据（F4）：点开看的用户就是要真实命令/文件名的那批，对他们隐藏对象=产品错误。受众重定位按用户判断定案：**会用电脑但不懂 AI 内部机制的好奇者**——术语是用户想学的，禁术语=抹杀点击动机。
3. **为什么三层缺一不可？** 对照实验证明（F1/F2）：只修喂料→黑话/电报腔仍在；只改提示词→解释者依旧对着空箱子编故事。喂料（P1+扩容）与 sysP（受众+结构+禁编造）独立成立，修法叠加。

### 5.2 裁决（三层，一个批次）

1. **P1 帧形态修复**（chat.tpl.html:1036）：`upd.content` 为数组时取各 `{content:{text}}` 的 text 拼接；同点兼容 rawOutput（shell 类取 `{stdout,stderr,exit_code}`，exit_code 存 card）。**影响面=工具卡输出区（sec-o）显示恢复，不只是解释**——验收必须含：跑一条 shell 命令，卡片输出区显示真实 stdout。
2. **喂料扩容**（前端载荷+桥端接收，research/19 §4 R1-R6 收敛）：
   - 载荷增：`input`（card._inp 截 1200，对齐展示上限）、`status`（completed/failed）、exit_code（有则带）、`toolName`（从 `_meta.goose.toolCall` 取，前端存 card——title 双形态兼容，不让模型从 title 反推）；
   - 空值无歧义化（R4 精神）：真无输出=「（该步骤没有返回文字）」；输出截断=标注截断；**禁止 (空) 歧义**；
   - 桥端 :3118 头截 600 改**尾截**与前端同向（600→600 恰好无事的现状是脆弱巧合，扩容前必须消掉静默截头错位）；
   - 缓存键纳入新字段（载荷变了，防旧缓存错命中）；
   - mojibake：sysP 内告知「输出可能含乱码，按上下文推断」；优先喂 content 文本块。GBK 转码本批不做（§8 触发器）。
3. **sysP 重写**（chat-bridge.tpl.js:3124 一处字符串，research/19 §4 P1-P5 + research/20 §2.5 七条范式收敛）：
   - 受众=会用电脑但不懂 AI 内部机制的好奇者；**删「禁止任何技术术语」「不复述路径」两禁令**；
   - 术语处理=准确名词+内嵌一句话解释（「执行了一条命令（command，让电脑做具体事的指令）」）；
   - 必答三问：①做了什么动作、对什么对象（点名真实工具名/文件名/命令前若干字/URL/表名）②结果是什么（成败+关键返回值：版本号/行数/报错原因）③对任务意味着什么（一句话，可选）；
   - **禁编造**：「信息没有提供就明说没提供，不要猜」；禁编造系统里不存在的类比对象；
   - 失败专用分支（status=failed/exit_code≠0 先行触发）：四段式=说清失败+错误要点（引用真实报错关键词）+最可能原因/下一步+需不需要用户做什么（B2 样本可作 few-shot）；
   - 长度 2-4 句、60-150 字、正常陈述句（禁电报腔）；max_tokens 300 / 500 字截断 / sha1 缓存 / 流式全保留（research/19 P5）。

### 5.3 明确不做（主线 4）

- **双层解释卡**（三句版+技术版展开，research/20 §3-B4）：好方向，本批不加 UI——先把单层修对。挂触发器 §8。
- **GBK→UTF-8 桥端转码**：成本不成比例，content 块+sysP 兜底先行。挂触发器。
- **live_output 流式分片喂料**：content/rawOutput 已覆盖语义，增量信息小。裁。
- **explain 载荷带对话上下文**：解释对象是单步工具调用，三问靠 _inp/_out/status 已可答；带上下文=token 膨胀+缓存失效率上升。裁（观察：护航期「第三问答不准」≥2 次再议）。

### 5.4 验收标准（主线 4，全批）

1. **显示恢复（GUI）**：dev 栈真会话跑 `git --version` 类命令 → 工具卡输出区显示真实 stdout（sec-o 非空，首次恢复的显示面）；失败命令卡显示真实报错文本。
2. **13 条载荷回归**（复用 tmp/r19-explain-probe，注意缓存需微调 title）：Arm B 系列（B1-B4）逐条答对三问、无 FM-3（黑话）/FM-4（电报腔）；**新增「输出未知」载荷**（不喂 output）→ 解释显式说「输出未提供」而非编造。
3. **可证伪标准**（research/20 §3-B5）：每条解释文本出现至少一次真实对象名（工具名/文件名/参数值/版本号）；失败样本解释含「失败」语义+真实报错关键词；全样本 grep 无编造类比对象。
4. 缓存：同载荷重试秒回同文；载荷任一字段变化缓存不命中。
5. e2e-chat / fuzz 全绿不降线；解释性能不降（13 条实测基线 1.2-2.4s/条，回归不劣化明显）。

## 6. 主线 5：真正的消息撤回重写（只立框架，不定案）

### 6.1 用户要什么（验收线形态）

重发某轮用户消息后，**历史=改写后的消息，不是追加新消息**（ChatGPT 式回滚语义）：该轮及其后全部内容（assistant 回复、工具行）从会话历史消失，视图重放与模型上下文一致呈现改写后形态；「取回修改」与错误卡自动重发红线（batch1 §4.2-5）零触碰，两者共存。

### 6.2 框架要素（补篇裁决必答）

1. **交互形态**：B 型（从 user 行截断到尾，21 实验 B/RB 验证的形态）vs C 型（原地改写，21 §4 不建议——残留回复对应不存在的问题）。倾向 B 型，补篇定案。
2. **手术安全**：坏行砖会话+误导文案（NEG 实验）→ 必须 BEGIN IMMEDIATE 事务+被删行备份（tombstone）+失败恢复路径；e2e 18c 节钉子形态=手术→load 重放断言历史无原句→prompt→回文，含手术失败可恢复分支。
3. **最大改动面**：前端消息无 goose message_id 映射——桥需在转发 session/update 时透传 `meta.goose.messageId` 并由前端保存（或桥自维护 sid→行号索引）。这是补篇裁决的成本大头。
4. **联动面**：busy 门（手术瞬间不得有 prompt 在飞）；多客户端（另一订阅者重跑 openSession 看到新历史）；usage 累计列不修（历史用量语义）；extension_data/工作区制品不回滚（/api/vcs 兜底，与「取回修改」一致）；归档索引/workspace-map 键=sid 不变零改动；**升级预案必查 v1.46→v1.49 messages 表/load 行为差异**（本轮实验全部锚定 v1.46）。
5. **触发器事实**：batch1 §5-T3（真机诉求≥2 次+PM 重新归约）——用户今日点名=显式诉求第 1 次，且直接给了形态要求（历史=改写后），归约输入已在。T3 的「PM 重新归约」即补篇裁决本身。
