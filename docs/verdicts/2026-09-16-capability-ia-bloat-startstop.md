## 1. 归约与三问

**词汇归约**：用户说「本事和技能归类重叠」，字面是两块面板，实指三件事——①两个入口在答同一个问题（「它会什么」），用户无法预测去哪找；②MCP 这个实体的生命周期被按动作拆到两地（装在一处、开关在另一处）；③已有搜索的清单缺结构化过滤维度（来源），找回性能停在「能搜」没到「能筛」。第④点「启停」则是 s87 用单一受众画像（零技术妻子）推出的「观察>治理」结论，撞上了 AGENTS §6 的真实受众定义（内测期硬核技术型）——s87 的受众前提对内测期不成立，但其为妻子守住的边界（零术语主面、对话通道兜底）全部保留。

三次为什么：
1. **为什么「本事/本领」同义是缺陷而不是小事？** 每个入口的成本是用户的一次记忆，记忆必须买到别处买不到的回答。「自带的本事」（出厂就有：数据库/浏览器/记忆）和「学会的本领」（可添加：技能）在产品里是两类实体、两套生命周期，但词汇没有承载这个区分——用户只能靠试探。修法是让词汇承载区分（自带 vs 学会的），不是消灭其中一个入口。
2. **为什么 MCP 开关该搬回插件 tab（s57 曾把它搬进本事）？** s57 修的真缺陷是「已装 MCP 没有任何可见开关」（盲区），修的位置选了能力面板——当时合理（能力面板是唯一的开关面）。但 s94 之后家/分职纪律确立：**实体的操作跟着它的生命周期走**。MCP 的装/卸在🔌，开关却在🧠，正是用户点名的「装完去哪开」路数不清。盲区修复的价值维持，位置随本裁决归位。
3. **为什么「停」必须明示「下次启动会自动回来」而不是做持久停用？** 持久停用=改写聚合源（apps/ 改名/标记）=新写通道+升级保护语义+agent 注册协议三面耦合，M 级成本换一个尚无实录的需求。运行态停+同卡诚实文案+对话通道兜底（「想彻底不要，跟小 forge 说拆掉」）已闭合主路径；持久禁用挂触发器。s87「她停了忘了→更困惑」的担忧，解药是状态常驻同卡（⏹徽章+▶钮+人话注），不是不做。

三问回答（合并四主线）：
- **用户何时遇到？** ①②每次打开管理面板/技能弹窗即遇到（心智建模持续失败）；③每次 app 出错或想腾资源时；④排障/治理时。
- **不用它怎么死磕？** ①②靠试探和问人；③现状零出路（只能重启全部或找 agent）；④排障只能开 pc 日志文件（开发者路径）。
- **做错的代价？** 本批以收窄/搬位/补维度为主，无破坏面；最大风险是写文案引入术语（R4）或顺手加功能（scope creep）——红线见 §5/§7。

### 4.2 最小启停规格

**S3a 桥端：POST /api/apps 写通道**（chat-bridge.tpl.js :3132-3137 改造）
- 方法语义：GET 维持现状（appsOverview 零改动）；新增 POST {id, op}，op∈{'start','stop','restart'}。
- **安全面（写通道三道闸）**：
  1. id 白名单=appReadRegistry() 命中的 app id（请求只送 id+op，**进程名从注册表推导，绝不从请求体取**）；
  2. 推导出的每个 proc 名过**基础设施 deny-list**（初值从 conf/process-compose.yaml 全量核对：chat-bridge/postgres/pg-init/faucet/nats-server/goose-scheduler/daily-backup/memory-mcp 等，UNVERIFIED-F12④ 工程侧核全后写死常量）——命中即拒 `参数不合法`（防御纵深：ADR-0003 禁 agent 定义基础设施键，聚合器是文本拼接不可信）；
  3. Origin 校验走 handleHttp 顶部全局规则（同现有 POST 端点）。
- 执行：stop 一次多参调用 `pcExec(['process','stop',...names])`（F7 多参支持）；start/restart 逐名顺序调用（await 串联）；pcExec 10s 超时沿用。
- 响应：全部成功 `{ok:true}`；任一失败 `{ok:false, err:'〈应用名〉没〈停/启动/重启〉成——跟小 forge 说一声，让它看看怎么回事。'}`（人话兜底，pc 原始 stderr 不透传）；pc 联系不上→`{ok:false, err:'进程管家暂时联系不上，稍后再试。'}`（appsNote 同族口径）。**无持久化**（不改任何文件；schedule.json/apps/ 零触碰）。
- 降级路径：op 非法/未知 id→400 形 `参数不合法`；readJsonBody 坏 JSON→既有坏包路径。
- 验收断言：①未知 id→ok:false；②fixture yaml 进程键=基础设施名（如 postgres）→ok:false（探针种子，用后自清）；③合法 fixture app stop→list 中该组 is_running=false→restart→true（活体）。

**S3b 前端：apps 卡片启停钮**（chat.tpl.html appsPaint :1947-1970）
- 载体：动作区（「打开看看」旁）加一枚状态驱动钮：run→「⏹ 停止」；stop/fail→「▶ 启动」；absent→「▶ 启动」（F12③ 验证前 absent 按钮可先渲染，若 start 对 absent 无效则按验证结果收窄为仅 stop+fail 可启）。fail 态可另加「⟳ 重启」次钮（restart 通道现成，op 枚举已含）。操作中按钮禁用，完成 loadAppsUI() 重拉重绘。
- **无确认框**（可逆+状态常驻同卡；定时暂停 ⏸ 同判先例 :1612）。
- **「停」的语义文案（写死，防 s87 担忧的「停了忘了」）**：UI 发起 stop 成功后，该卡片 state=stop 时追加一行 fnote（前端记 appsUserStopped[id]，会话内有效）：「**已停。下次启动数字员工时它会自己回来；想让它彻底别再回来，跟小 forge 说一声拆掉。**」——首句=结构性事实（F8 聚合语义；F12② 活体验证项），次句=对话通道兜底。
- 按钮人话：aria/title「先停一停（下次启动数字员工时会自己回来）」/「启动这个应用」。
- 验收断言：①run 卡停→徽章 ⏹+「已停…」注在场+钮变 ▶；②再启→✅+注消失；③失败→alert 人话、按钮恢复。

**S3c 探针与 e2e 适配义务**
