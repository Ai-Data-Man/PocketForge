## 1. 根因归约：为什么触发式声明没满足用户（同一问题第三次）

**用户要的不是「现在清单短」，是「膨胀可能出现的地方，找回机制已经建好」。** 用结果思考：用户验证产品的方式是打开界面看，不是读代码注释。s95 的误判链条：

1. **判据选错**：s95 用「终态规模预期」定形态（apps/sched 声明终态 <30 → 9-30 档 → 只补搜索，分页挂 >30 触发）。但 apps/sched 的增长引擎是对话/agent 驱动——「终态 <30」是拍出来的数字，没有任何机制强制它不越界；增长恰恰由用户自己每句「帮我做个××」推动，是最活跃的引擎。给最活跃的引擎挂最弱的护栏，是错配。
2. **声明不可见**：R2 声明活在代码注释和裁决书里。用户打开 🚀 面板看到的是应用一长条往下滚——在他视角里，「>30 再加分页」的承诺等于什么都没有。
3. **声明不可信**：触发式条款依赖「有人注意到超阈 + 有人排期」，在自治团队里等于又一轮 s95 式补课。历史上这个问题 2026-09-05（§30-31）→ 2026-09-16（主线②）→ 今天第三次——前两轮的处置都没能让用户停止提出，本身就是证据。
4. **同屏不一致暴露欠账**：同一个管理面板里，made 有 chips+分页、db 有分组+分页、ins 有 chips+分页、mem 有渐进+搜索——唯独 apps/sched 连分页调用都没有。用户点名「技能」和「管理小forge」正是这两处机制密度的落差带。ins 从未被点名，因为它的机制在。
5. **「搜索缺有效过滤维度」同源**：文本搜索解决「我知道关键词」；维度过滤解决「我要某一类」。「哪个应用出错了」是排障第一问，而 fail 卡按 run 在前的排序**沉底**（chat-bridge:1986）——混排里最该被找到的反而最难找；「哪些任务暂停了」是静默遗忘源（暂停的任务不跑、不出声）。s95 D5 给 sched chips 挂触发器，与分页触发器同错。

**关键区分（本裁决的裁刀，须写进规范）**：ins 的「>SKILL_N 才出现翻页器」与 apps 的「>30 触发分页」字面相似、本质相反——

- ins：**机制已建、UI 阈值内隐藏**。pageSlice 代码路径每次渲染恒走，pagerPaint 在 pages≤1 时自动不渲染。机制的存在不依赖任何未来动作。
- apps/sched（s95 后现状）：**机制完全没建**。渲染函数里没有分页调用，只有一行注释承诺未来补。机制的存在被推迟到一个无人盯守的触发器。

前者是合规的形态设计（阈值内零视觉噪音），后者是触发式欠账。R2 原文「31-100 条分页」把「机制存在」与「机制可见」混在一句话里，才让 s95 有空间做出「声明代替建机制」的处置。本裁决 §3 在规范层把两者拆开。

## 5. 非目标与红线（与目标同等重要）

1. **桥侧不动（结论：不需要护栏，且护栏与本机制互斥）**：GET /api/apps、/api/schedules、/api/memory 维持全量返回。理由：①S4 的 chips+搜索+分页全部在前端全集（appsAll/schedAll/memAll）上过滤——**桥侧截断会直接破坏内建过滤**（截断子集让 chips 命中数与过滤结果失真）；②响应体线性小（apps 每行约 300B，200 个≈60KB，localhost 无网络开销）；③真实规模化成本在子调用而非行数（listenPorts budget=8 已护栏+截断标记，pcProcMap 单次调用）。db 的 200 表护栏是例外且维持（表行元数据获取有真实成本；db 找回按名走搜索，不依赖全集 chips）。不做服务端分页/游标/虚拟滚动。
2. **零术语红线（妻子面）**：chips 文案全部沿用行内既有词汇（✅ 运行中/⏹ 已停/⚠️ 出错了/排着的/暂停的）；state/paused 等键名只存在于代码，不上界面。
3. **最小 diff**：全部复用 pageSlice/pagerPaint/skillsChips 模式与既有样式串；不改任何端点形状；apps 卡片结构、启停钮、日志子区、排序零触碰；sched 行结构零触碰。
4. **mem 不动（非目标维持，理由升级）**：s95 §7-6 维持，但理由从「合规形态维持」升级为「R4 阻塞」——分类名=memory/*.txt 英文文件名，chips 化会让英文文件名成为一级筛选控件，而分类无建时人话元数据可挂（R4：解释来源=系统元数据>结构性事实，UI 只消费不猜）。**解锁前置=记忆分类获得建时人话说明（数据管线义务），不是规模触发器**——这与触发式欠账性质不同：缺的是数据不是机制承诺。
