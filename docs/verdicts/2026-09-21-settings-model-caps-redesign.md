## 1. 归约（每条主线真问题一句话）

1. **主线1**：不是「缺左导航」，而是 ⚙️ 把三个互不相干的信息域（服务商连接 / 外观 / 关于与升级）塞进同一个滚动容器、且滚动容器=整个弹窗（chat.tpl.html:575-623，CSS :239 `#panel{max-height:86vh;overflow-y:auto}`）——滚动无归属、域间无边界，找设置=扫全卷。修的是**信息域分区与滚动归属**，左导航只是形态。
2. **主线2**：不是「文案难看」，而是**能力配置没有按「服务商 API 规范 → goose 消费面 → 桥翻译 → 小白呈现」四层抽象逐层翻译**：桥内部机制词（variant=「快/深换模型」、顶栏 title「想深一点会换成完整版模型」）未经抽象直接刷给妻子；同时 ZCode 式字段体系该裁的没裁（无机制消费面的字段当可配置旋钮=新一轮假把式）、该有的没有（variant 配对的能力语义、识别来源标注）。预设 9router 是同一病根的出厂形态：把开发期占位当缺省值交付。

三次为什么：为什么滚动找设置劣质→因为域无边界；为什么域无边界→因为 ⚙️ 从「一个表单」长成「三块堆叠」从未按域重划；为什么要按域重划→因为设置的唯一用户（妻子）没有技术地图，空间分版就是她的目录。为什么能力配置垃圾→因为机制词直达用户面；为什么机制词直达→因为 s98 落地时呈现层只做了「零术语换词」没做「抽象重译」；为什么要抽象重译→妻子的心智模型是「它有什么本事」，不是「参数怎么路由」。

## 2. 设计A：⚙️ 弹窗左侧分类导航

### 2.1 scope 裁决：🧠 与 ⚙️ **不合并**（本批）

- 理由：①用户只点设置模块，扩展合并=大爆炸（🧠 七 tab 的 r5 词汇审计、semantics-r5 探针扫描面、ia-logic 锚全要动），违背最小 diff 与内测期「验证优先于扩张」；②两入口心智分界成立且已有母句：⚙️=「它怎么连、长什么样、怎么升级」（配置域），🧠=「它有什么、干了什么」（能力与台账域）——对应 ZCode 的「基础设置」vs「Agent 能力」分组，分组边界一致，只是 ZCode 用一页左导航承载、我们用两个入口承载；③🧠 已是 tab 分区结构（chat.tpl.html:489-497），**不存在主线1 的线性滚动病**，合并的收益只是「少一个入口」，代价是全量探针迁移。
- 边界句（写入两弹窗副标题，S4 落地）：⚙️=「连到哪、长什么样、版本新旧——都在这」；🧠 既有句不动（chat.tpl.html:488）。
- 合并触发器（满足其一即立项，合并时直接复用本批左导航骨架）：①内测反馈出现「在 🧠 找设置类 / 在 ⚙️ 找能力类」≥2 例；②⚙️ 左导航类目自然增长 >5；③用户明示。

### 2.3 视觉形态与窄窗降级

- 形态：modal 内左导航竖列（约 150-170px：图标+类目名，选中态=背景药丸+左侧强调条，ZCode 设计语言的 modal 尺寸适配）+ 右内容区。**宽度 520→约 780px**（`max-width:calc(100vw - 24px)` 与 `max-height:86vh` 不变，:239）。**关键机制：`overflow-y:auto` 从 #panel 下移到右内容 pane**——导航与右侧大标题恒在视口，滚动只属于内容。右侧顶部=当前类目大标题+母句副标题（ZCode 骨架）。
- 窄窗降级（<640px 视口或 modal 实宽 <640）：左导航隐藏，顶部横向类目条——**复用 .rtab/.mtab 既有样式与 🧠 先例**（:489-497），同一 switchPane(id) 逻辑驱动两种形态，不写第二套状态机。
- 标题改「⚙️ 设置」，aria-label 同步「设置」。

## 3. 设计B：模型能力体系

### 3.1 内部抽象对齐 goose 真实消费面（四层表）

| 层 | 事实 | 出处 |
|---|---|---|
| ①服务商 API 规范 | OpenAI 兼容：host/key/models 列表；glm 线参数通道（thinking.type/reasoning_effort）行为死透（5样本×5臂） | research/35 §3、research/37 §2-3 VERIFIED-RUN |
| ②goose 消费面 | 消费=模型名（spawn env GOOSE_MODEL，env 旁路目录校验）+ OPENAI_HOST + thinking_effort 五档（仅 is_reasoning_model 名单模型）；**不消费**：max_output_tokens、输入类型复选、结构化输出等任何能力字段；declarative request_params 通道在 glm 线行为死 | research/35 §1-2、STATE.md:3；spawnAcp env chat-bridge.tpl.js:948-956 |
| ③桥翻译（llmproxy，零改动） | caps 注册表 variant 条目→家族表→别名 gpt-5-forge-\<fast\>→effort off/low/medium→快、high/max→深→真名；梯度提示 gradient 只在桥内生成 | chat-bridge.tpl.js:730-745/:779-798/:1283-1320 |
| ④用户呈现（本批重做） | 编辑器+池行+顶栏挡位 | §3.3-3.5 |

**消费面裁剪判据（本裁决立规）**：一个能力字段只有在存在机制消费面（影响某条请求/某个 UI 行为）时才允许进用户面；纯展示字段=信息行（可看不可调，或折叠进技术区），**禁止伪装成可配置旋钮**。据此对 ZCode 图1 骨架裁剪：上下文窗口→信息行（折叠技术区，见 §3.3）；最大输出 Token/输入类型复选/模型能力复选（结构化输出等）→**不搬**（无消费面）；推理等级标签按钮→不搬（levels 恒 ['low','max']，见 §3.2）；推理参数映射→不搬（参数通道已证死，搬=假把式）。

现状核对：context_len 与 multimodal 当前消费面=**仅展示**（chat.tpl.html:1108-1115 池/顶栏 bits；桥内无其他读点，grep 亲核）——如实定级为信息行，不是缺陷但编辑器不得暗示「改了会怎样」之外的效果。

### 3.2 model-caps schema 演进裁决

- **字段集不变，_schema 维持 1，不升版**：现有 `{context_len, context_est, multimodal, thinking:{mode,levels?,variant:{fast,deep}}, user}`（chat-bridge.tpl.js:738-745）已完整覆盖消费面（variant 驱动家族/别名/翻译，levels 预留三档）；本批改的是呈现不是结构。
- **补一件 ADR-0009 欠账**：data/model-caps.json 带 _schema:1 但**未注册进 STATE_SCHEMAS**（chat-bridge.tpl.js:484-507 无此键）——S2 顺手补登记 `'model-caps.json':{latest:1,steps:{}}`（零迁移，纯纳入 migrateJsonAt 伞下）。此后任何字段演进=同提交 _schema+1+注册表迁移步骤+迁移自测（ADR-0009 纪律明文）。
- 未来加字段的触发器：仅当桥/goose 出现新消费面（例：multimodal 用于图片上传预检）时才立项，加字段同批建消费点。

### 3.3 能力编辑器重做（ZCode 图1 骨架人话化）

入口不变（#model-pool 每行「能力」按钮→面板内嵌编辑器，:2440-2441）。新结构：

```
「{模型名}」的本事
——下面这些是按名字自动认的，认错了您改；改过就记住您的。
① 能不能看图        [能看图 ▾]（她贴照片时用得上）
② 快慢怎么调        ○ 它自己定（顶栏没有快慢选择）

                    ○ 给它配一个深档（顶栏出现「快一点 / 想深点」）
                      深档用哪个模型：[池内同服务商模型 ▾]
   说明句：深档＝干这活时让它用更完整的那个模型，更准，也更花时间。
▶ 技术细节（平时不用动）
   上下文大约多少字：[____]（能一次读进多少字；不知道就留空，按估计显示）
```

- **措辞禁令**：编辑器与顶栏全用户面**禁用「替换/换成另一个模型/变体」**等机制内幕词；深档配对在编辑器里可以点名模型（她正在配置它，不点名无从配置），但框架=「给它配一个深档」（能力归属），不是「想深点时换成 X」（机制操作）。现状违例原文：select 选项「快/深换模型（想深点时换成另一个模型）」(:2475)、子行「想深点时换成：」(:2478)——S2 删除重写。
- 上下文长度从主面**降级进折叠技术区**（ZCode「高级配置折叠」骨架的人话化；details.tz 复用技能弹窗先例 :469）：现状主面三字段并排 (:2483-2485) 把展示型字段抬到与行为字段同级，正是「没有合理抽象」的呈现面。

### 3.6 预设 9router 处置：出厂空态+引导，删死地址（本批修）

事实（两实体，均亲核）：
- **(a) forge/conf/goose/config/custom_providers/forge-router.json**：git 追踪、package.sh 不剔除（SKIP :97 与 rm 行 :25 均无 custom_providers）→**随每个出厂包发行**，内容硬编码 9router 本地中转 `http://127.0.0.1:20128/v1` + mimo-v2.5/deepseek-v4.1-flash 预设 + 描述「交付时改 base_url 与 key」（开发占位语）。
- **(b) bootstrap.ps1 首启种子回落**：providers.json 缺失/无活跃档 → 种死地址+mimo-v2.5（:131-133；写入 :152-165；F-11 字面自愈 :177-179 匹配这两个字面值）。

裁决：**空态+引导**。理由：①未配置态是**已被设计的一等 UX**——健康判定 `!host||!model`→不探→key-guide 黄条「还没连上大模型」+ welcome 引导卡（chat-bridge.tpl.js:879；welcome.tpl.html:32）；②死种子使 host/model 非空→探测→127.0.0.1:20128 拒连→**红条「联系不上大模型服务商」**+welcome :37 的换线指引（那是给「线路坏了的已配置用户」的话）——出厂首启即误诊为故障，比空态差（静态代码级结论，见 §7-1 待沙盒定案）；③「fail-safe 死地址」防的是空 env 崩溃，但 (a) 的 spawn 链实为 env 全量自给（chat-bridge.tpl.js:948-956 GOOSE_PROVIDER/GOOSE_MODEL/OPENAI_HOST 显式注入），declarative 文件在当前产品线上无消费点（UNVERIFIED 残留：goose 模型目录校验是否间接依赖它，S3 沙盒定案）。

工程处置（S3）：
1. `git rm forge-router.json`；package.sh rm 行补 `conf/goose/config/custom_providers`（目录级，防再犯）。
2. bootstrap.ps1 出厂回落改空值（$pvHost=''+$pvModel=''+$pvKey=''）；**F-11 字面自愈块 (:177-179) 逐字保留**——它匹配的是存量旧部署的种子字面值，与新出厂空值无交集；幂等补缺 (:186-189) 空值补空键，行为同退化档先例（:141-146 注释已确立「种空值而非缺省」原则）。
3. 取舍声明：若沙盒证空 GOOSE_MODEL 令 goose spawn/session 崩溃环→回落臂=仅空 host（`!host` 同样进未配置态），model 保结构合法值；两臂都崩才保留死地址并如实记入本裁决修订。**不许第三种「看似合法的占位档案」**——那是换皮的 9router。
