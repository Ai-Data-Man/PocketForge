# 裁决：思考内容留痕——回放按消息挂靠 + live 回合就地收进（通路 A）

日期：2026-09-30 ｜ 主控：s105 ｜ 依据研究：docs/research/48-thought-persistence.md（Q1/Q2/Q3 全 VERIFIED-RUN 2026-09-30，源码链 VERIFIED-DOC goose v1.50.0 tag）｜ PM：pf-pm

## 0. 一句话

用户触发原话（2026-09-30 主线，过门条件）：「思考内容展示，虽然可以点开折叠看，但是一等想完就再也看不到了，这体验就非常差，假如想回头审查，根本没有留痕」。

留痕通路**已经存在且全程在工作**：goose 一直把思考存进 sessions.db（6 周 1301 块/247 会话，research/48 Q1）→ session/load 回放把每个 thinking 块转 `agent_thought_chunk` 帧全文发出、带 messageId（Q2）→ 桥纯透传（§3.2 零解析）→ **前端收到后丢弃**（Q3：chat.tpl.html:1276 `setBusy(false)`→`thinkDiscard()`，:1494 首正文帧同样弃置）。「不留痕」的真凶是前端消费端。

裁决：**只改 chat.tpl.html**。回放期的 thought 帧按 messageId 挂到对应 assistant 消息内的折叠块；live 回合结束（首正文帧/收忙）时思考内容就地收进刚落地的回答——与回放同形态。桥 / goose / sessions.db **零改动**。本裁决 supersede s103/S2 母句「收起后不留在对话里」承诺（§3.3）。

## 1. 归约（三问）

| 问 | 答 |
|---|---|
| 为什么说「根本没有留痕」？ | 现有 S2 面板是**忙碌域瞬态件**：`thinkBuf` 在回合结束被 `thinkDiscard()` 清空，回合后无任何载体。用户看到的是「想的时候能看、想完就没了」。 |
| 为什么想回合后还能看？ | 回头审查——想知道模型当时**怎么想的**：复核答案的推理路径、归因错误回合、验证信任。审查对象是**具体某条回答**的思考，不是全库浏览。 |
| 为什么现有机制不够、必须新建载体？ | 库里一直存着（Q1），回放一直发着（Q2），缺的只是前端把帧**挂到消息上**而不是丢掉。不需要任何新存储层、新机制、新桥面。 |

**用户真实任务（一句话）**：回合结束甚至多天之后，在对话流里找到某条回答，点开看它当时想的过程——路径 ≤2 步（§6）。

## 2. 通路裁决（负验证）

**通路 A（采纳）＝纯前端消费端**：回放帧按 msgId 缓存-配对挂到 assistant 消息；live 帧同款收留。前提 Q1/Q2 双 VERIFIED-RUN——即插即用，历史会话（2026-08-19 起 247 个带思考会话）即刻覆盖。改动面仅 chat.tpl.html（research/48 §4 估 30-60 行）。

**通路 B（否决）＝桥读 sessions.db 补发**。负验证：B 解决什么 A 解决不了的问题？——唯一候选=「goose 回放行为变化时的兜底」，属假想触发器；现行栈回放已含同样数据（Q2 活体三例），桥再查库补发＝**同帧双份 + 补发帧与原生回放帧交错顺序不受控**（research/48 §4-B）。无 A 解决不了的现实问题 → 多余，否决。

**通路 C（否决）＝桥自建双写落盘**。负验证：C 的独有价值只有两个——存「直播逐帧原文（goose 合并前碎片）」或覆盖「goose 不落库形态」；现行栈两者皆无需求（Q1 证明落库从来在做）。代价=同一数据两处存，且 `rollbackRewrite` 只删库行、桥文件会留**已撤回内容**，直接违反 G6「删除内容不复活」红线，除非同点联动清理（research/48 §4-C）→ 改动面最大、红线风险最高，否决。

**红线重申（工程约束）**：桥零改动是目标。若工程发现 live 帧 msgId 缺失必须桥补——停手，回主控重新对齐，不许自作主张扩桥。

## 3. UX 形态裁决（句级）

### 3.1 历史回放：挂哪、怎么呈现

- **挂哪**：每条 assistant **正文消息内部**的折叠附属块（`div.msg.agent` 内、操作条 `msgButtons` 同层），先例=工具卡/操作条（消息内附属件，research/48 §3.4 挂点测绘）。
- **归属规则（live 与回放同一套，按 msgId 配对而非相邻性——research/48 §4-A 风险①，20260819_10 例 thought 与正文中间隔着 tool_call）**：
  1. thought 帧按 messageId 匹配 assistant 正文消息（正文帧与 thought 帧同 msgId=同库行，Q2 活体①）→ 挂该消息。实现上 assistant 消息需补挂 `dataset.gmid`（user 侧 :1495 已有同款先例）。
  2. 匹配不到宿主（msgId 对应的库行是 thinking+toolRequest 行，前端呈现为工具卡、无 assistant 正文元素——Q2 活体③）→ 挂到**其后第一条 assistant 正文消息**。用户语义成立：这段思考是「决定调工具前的规划」，审查时序上先于答案，挂在答案下位置感正确。
  3. 回合结束仍无正文消息（零正文帧的断线回合）→ 弃置。理由：goose 只在回合循环末落库（research/48 §1.3-3），纯断线回合库内无 assistant 行、回放也不会有——**前端挂靠集 ⊆ 库内持久行**，不留刷新后消失的幽灵块。
- **一回合多条 assistant 消息（工具回合）**：各挂各的——每个 msgId 的思考挂各自宿主消息，规则 2 兜底的挂下一条正文。不合并成单块。
- **默认折叠**：折叠态只是一个按钮，**点开才渲染文本**（护栏，§3.5）。
- **按钮文案（人话，句级定死）**：折叠态「`它当时怎么想的 ▸`」；展开态「`收起 ▴`」。与忙碌域 live 入口「看看它在想什么 ▸」（chat.tpl.html:374）词族一致（「在想什么」），时态词「当时」标明留痕属性——用户学一次，两个入口不混淆。
- **无思考回合**：无帧不出现钮（research/48 §5-2 诚实口径，内容不造假）。

### 3.2 live 回合：想完即弃 → 就地收进

- **忙碌域不动**：回合进行中，S2 面板（think-peek/think-draft）照旧流式——`thoughtFeed` 喂 `thinkBuf`、面板可开合，体验与 s103/S2 完全一致。
- **收留时机**：现 `thinkDiscard()` 的两个触发点即收留点——
  - :1494 首个 `agent_message_chunk` 到达（「想完开口说话」）：收起忙碌面板的**同时**，把当前 thinkBuf 落进**该正文消息**的折叠块（归属规则 §3.1 同款：live 帧若带 msgId 则按 msgId 配对，配不上挂本条正文消息）。时序上无空窗：面板收起的瞬间，内容已可在消息下点开。
  - :1276 `setBusy(false)`（回放收口/异常收忙）：live 态回合结束仍无正文消息 → 按 §3.1 规则 3 弃置。
- **live 帧 msgId 工程核实（前置红证，T2 第一件事）**：research/48 §2.2-2 源码级（VERIFIED-DOC）证明直播与回放共用 `content_chunk_for_message`——**直播帧同样带 messageId**；但活体只验了回放臂（research/48 自记验证面）。工程须用现行栈真回合抓 live `agent_thought_chunk` 帧核实 msgId 在场。**容差（两分支都写死，不许现场发挥）**：
  - 分支甲（帧带 msgId，预期命中）：live 与回放走同一套缓存-配对逻辑，两态归一。
  - 分支乙（帧不带/桥剥）：归属规则=**挂当前流式中的 assistant 消息（streamEl）；streamEl 未出生则挂回合内下一条正文消息**。工具回合中段思考（宿主是 toolRequest 行）照此落最终答案消息——与回放态规则 2 的近似归属同向，两态形态一致。
- **回放态不再喂 thinkBuf**：openSession 期间 thought 帧走挂靠缓存（回放期忙碌面板本就不可见），`:1083` 收口的 thinkDiscard 对挂靠缓存无操作——回放帧不再经过「喂进再丢弃」的死路（research/48 §3.1 点名的现状）。

### 3.3 supersede 节（显式立此存照）

**s103/S2 承诺「收起后不留在对话里，对话只留正式回答」自本裁决起废止**，代之以「收起后收进这条回答下面」。s103/S2 其余全部维持：忙碌域面板形态、折叠交互、32KB 尾窗（瞬态观察口径）、「无帧不出现」诚实口径、「原文可能是英文」提示。主控在 STATE/journal 落 supersede；使用说明同步见 T4。

### 3.4 母句改写（R1 母句纪律：三问可答、零术语）

- **td-note 新句**（chat.tpl.html:374，只换「变了什么」段，其余逐字保留）：
  > 这是它干活前边想边说的草稿——从哪来：模型自己边想边写的（原文可能是英文）；怎么变：想到哪更到哪，只露最后一段，想完开口说话就自动收起；**变了什么：收起后收进这条回答下面——点「它当时怎么想的」随时回看。**
- **消息附属块母句**（新块内一行说明，展开块顶部）：
  > 这是它当时想的过程——从哪来：回答前模型自己写的（原文可能是英文）；怎么变：已经想完，不会再变；变了什么：留在这条回答下面，重开对话也还在。

三问自检：两块母句各自「从哪来/怎么变/变了什么」三问可答；双向划界（R1 执行口径增补）——忙碌域面板：「正在想、会动、只露尾段」；消息附属块：「想过、不动、全文」——什么时候看哪边一句话可答（想的时候看上面的，回头审查看回答下面的）。

### 3.5 体量护栏（硬要求）

- **默认折叠 + 点开才渲染文本**：折叠态 DOM 只有按钮，全文存 JS 侧（挂靠缓存/dataset），点开才注入 `pre`。历史会话（247 个带思考会话、单会话最坏 29,345 字符，research/48 §3.5）多回合全渲染的 DOM 累积由此归零。
- **不截断**：留痕的意义=看全，「看不到一截」=复刻本裁决要治的病。13,088 字符最坏块点开必须能看全——展开块 `max-height` + 滚动（#think-draft 38vh 同款机制）。
- **「原文可能是英文」沿用**：两处母句均已含。
- **live 臂尾窗注记**：live 收留用的是 thinkBuf（THINK_BUF_MAX=32768 尾窗，:1248）。单回合思考超 32KB 时 live 块会缺头——6 周实测 max=13,088，从未触发；若触发，刷新后回放块=库内全文（回放不走尾窗），自愈。注记不立项。

## 4. 信息架构过检（AGENTS §7）

- **R1 同页堆叠边界：过。** 思考块是 assistant 消息的**内部附属件**，不是新实体、不构成并列清单——同容器合法性=它与消息正文是同一实体（同一库行）的两个生命周期面（想 vs 说），先例=工具卡/操作条（消息内附属件，research/48 §4-A 同判）。两个呈现域（忙碌域瞬态面板 vs 消息域留痕块）是同一内容的两阶段，划界句见 §3.4。
- **R2 列表规模阶梯：不触发。** 块随 assistant 消息行生灭，每消息 ≤1 块，无独立增长引擎、无可滚长清单；护栏（默认折叠+点开渲染）已内建。
- **R3 配置归属：不触发。** 无新配置项。
- **R4 解释层义务：过。** 区块标题「它当时怎么想的」即人话，无英文实体名待解释；思考原文可能是英文属**数据内容**非界面标签，R4 不约束内容语言，母句提示已覆盖。

## 5. 非目标与边界（对什么说了「不」）

1. **不进撤回重写面**：rollback 删到某 user 行，其后 assistant 行（含 thinking）整行删除，回放自然没有——留痕随消息行生灭=正确语义，不新增任何撤回侧交互。桥文件双写的撤回联动难题正是通路 C 被否的原因之一。
2. **不做会话级「思考总览」新面板**：消费面判据——总览预设了「浏览全部思考」任务，用户原话是「回头审查」（审查对象=具体回合），无真实找回任务就不建新面。
3. **思考内容不进搜索**：chat 搜索搜正文；思考=「想过什么」而非「说过什么」，且原文英文居多、与正文语义重叠，进 hay 污染命中。除非未来出现真实任务（例：「找到它当时用 X 方案推理的那次」）再立项，本批不做。
4. **不做思考编辑/导出/中文化**：无用户信号；中文化会伪造留痕（留痕的价值=原文）。
5. **桥/goose/库零改动**（§2 红线）；不改 THINK_BUF_MAX（尾窗是忙碌域瞬态口径，不动）。

## 6. 消费面判据过门

留痕的消费入口=**消息内折叠钮**：打开任意会话（回放）→ 点目标回答下的「它当时怎么想的 ▸」→ 看全。2 步。live 回合：回合结束 → 同一钮出现在刚落地的回答下。2 步。无菜单、无面板、无新导航——消费面与内容同址。
